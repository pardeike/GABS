# GABS v1.1.0 release notes

GABS 1.1.0 adds named launch profiles, declared typed launch inputs,
lifecycle hooks, hot config reload, shared MCP/CLI lifecycle handling, and
stricter runtime-state coordination.

## Upgrade order: binary first, config second

Upgrade every GABS binary that reads a shared config directory to 1.1.0 or
newer **before** adding `profiles`, `launchInputs`, `lifecycle`,
`defaultProfile`, or game-level `env`/`unsetEnv` fields. Check each installed
binary with:

```text
gabs version
```

A pre-1.1.0 binary will silently ignore those fields. It can accept the file
and launch the bare game-level command while dropping profile arguments,
environment values, launch inputs, and lifecycle hooks. A profile-enabled
config must therefore not be used with a pre-1.1.0 GABS binary.

An already-running launch from an older GABS remains manageable. On the first
non-read-only lifecycle operation, 1.1.0 validates and normalizes the legacy
runtime claim once; `games_connect` can also validate and migrate its legacy
endpoint once. Read-only status remains deliberately degraded until that
normalization occurs.

## Intentional compatibility changes

Four previously accepted input or configuration classes can now fail
explicitly:

- Core MCP tools reject unknown MCP arguments instead of silently ignoring
  them. Remove misspelled or obsolete fields from saved calls and client
  templates.
- `games_start` requires `timeout` to be an integer from 1 through 3600
  seconds. Out-of-range, fractional, and overflowing values are rejected.
- Config files containing duplicate JSON members are rejected instead of
  accepting the last value. Remove duplicate object keys before upgrading.
- Game IDs are validated when the config is loaded and must map to distinct,
  portable runtime directories. IDs such as `factory/`, `a//b`,
  `factory/../adventure`, absolute paths, backslash-containing IDs, and entries
  whose map key differs from their declared `id` are rejected. Distinct IDs
  that differ only by case or canonical Unicode composition are also rejected.
  Before upgrading, rename each affected map key and `id` to the same canonical
  spelling and choose one unique ID for every case/Unicode-equivalent group.
  Remember that renaming an ID also changes its mirrored tool namespace and any
  script or instruction that names it; stop old launches before changing IDs so
  no legacy runtime claim is stranded under the obsolete spelling.

These failures are intentional: they turn ambiguous calls and configs into
actionable errors instead of running with an unintended value.

## Converting several IDs into profiles

Only consolidate game IDs whose `target` and `launchMode` match. Before
removing the old IDs, account for all three externally visible changes:

- Mirrored tool namespaces follow the surviving game ID, so callers using an
  old ID prefix must update discovery or calls.
- Scripts and agent instructions that reference removed IDs must use the
  surviving ID plus `--profile` or the MCP `profile` argument.
- Separate IDs could run concurrently; profiles under one ID are mutually
  exclusive. Keep separate IDs when simultaneous instances are required.

The full conversion procedure and validation rules are in the
[Configuration Guide](../CONFIGURATION.md).
