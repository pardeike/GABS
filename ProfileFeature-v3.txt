# GABS Launch Profiles — Design v3

Status: recommended consolidated design for issue #66

Issue: https://github.com/pardeike/GABS/issues/66

This document combines the strongest parts of `ProfileFeature-v1.txt` and
`ProfileFeature-v2.txt`, resolves their contradictions, and adds the operational
requirements needed for profiles to be dependable in foreground, wrapped, and
detached launch setups.

The product model is deliberately small:

    stable game identity
        -> optional named launch profile
            -> optional declared, typed launch inputs

Profiles select repeatable launch context. Launch inputs provide bounded,
explicit per-launch variation. Structured lifecycle hooks make that selected
context observable and controllable. None of these becomes a second control
channel for the running game.

## Executive decision

Use v2's clearer product framing and profile-level `workingDir`, retain v1's
optional default profile, explicit reload verification, safer lifecycle exit
semantics, and installed-skill discipline, and add a shared lifecycle state
machine, secure runtime snapshots, strict config validation, environment
sanitization, and a non-destructive legacy mapping assistant.

The most important decisions are:

1. A game ID remains the canonical runtime, bridge, ownership, and
   single-instance identity. Profiles never create parallel instances beneath
   one ID.
2. Profiles may vary launch context (`args`, `env`, `unsetEnv`, `workingDir`,
   and lifecycle hooks), but not target, launch mode, effective `gabpMode`, or
   other configured game identity fields.
3. The MCP surface never accepts raw argv or environment overrides. It accepts
   only configuration-declared `launchInputs`, validated at call time.
4. A configured status hook participates in every liveness decision, including
   duplicate-start prevention, detached startup verification, GABP waiting,
   restart recovery, status, stop, and kill.
5. A failed or ambiguous lifecycle observation never erases active state and
   never authorizes another launch.
6. Existing version-1.0 configs continue unchanged. Enabling profiles is an
   explicit schema/behavior transition layered on the same game identity;
   ordinary legacy starts require no migration.
7. Mapping legacy entries is explicit and non-destructive. GABS separately
   classifies exact duplicates, same-identity profile candidates, and distinct
   identities, then produces a deterministic plan and proves resolver
   equivalence within clearly listed managed-identity changes. The user applies
   the edit; `games_start` never rewrites config.
8. Config reload is automatic, while `games_reload_config` remains available
   for deterministic validation, revision reporting, and agent workflows.
9. Every start pins one immutable config revision. Reload cannot produce a
   launch assembled from two revisions.
10. MCP and CLI use one transport-neutral launch/lifecycle manager. There is
    no second implementation with subtly different behavior.
11. Every MCP lifecycle interaction has a bounded caller wait. A request
    deadline may return a persisted operation as still in progress, but never
    makes an accepted stop disappear from status. A standalone CLI normally
    has the same bound; the only explicit exception is that it cannot exit
    safely while an OS-level workload/action creation primitive is already
    non-interruptibly in flight.

## What v3 takes from each draft

| Area | Best part of v1 | Best part of v2 | v3 decision |
| --- | --- | --- | --- |
| Product model | game -> profile -> declared input | clear goals and non-goals | retain the three-layer model with v2's framing |
| Profile fields | strict identity boundary | profile `workingDir` | allow launch-context fields, including `workingDir` |
| Default selection | default may be intentionally absent | omitted profile stays easy when a default exists | optional default; otherwise return `profile_required` |
| Per-launch variation | bounded `launchInputs`, not raw argv/env | JSON-Schema vocabulary | call them `launchInputs`, describe them with `type`, `enum`, `minimum`, and `maximum` |
| Lifecycle | 0 running, 1 stopped, other unknown | structured no-shell hooks | safe tri-state plus optional exit-code sets |
| Reload | automatic plus explicit reload tool | next-call discovery | automatic by default, explicit tool for verification |
| Legacy config | actionable manual recipe | ordinary starts remain untouched | zero-migration base behavior plus a read-only mapping plan |
| Documentation | update and install the repo-owned skill | keep detailed schema outside the skill | concise skill, detailed config guide, real install/check hook |
| Operational safety | immutable launch snapshot | cleaner resolver description | atomic private snapshots and a shared lifecycle state machine |
| Genericity | neutral protocol design | launch-context terminology | no setup- or game-integration-specific special cases; only declared launch-mode capabilities |

## Evidence from recent real use

The design was checked against local Codex interaction logs from 6 through 20
July 2026, using a conservative fifteen-day window. Static instructions,
memory-search output, and inherited subagent copies were excluded. Only two
top-level sessions contained actual GABS use; that concentration is useful
because they contain both interactive development and repeated isolated smoke
runs.

The larger interactive session recorded:

- 20 completed `games_start` calls: 19 connected during start, while one
  correctly returned process-started/bridge-pending with background
  attachment;
- nine completed `games_stop` calls, all successful, plus one additional stop
  that produced no result for more than a minute before the caller cancelled;
- 149 tool-name searches, 56 tool-detail calls, and 496 game-tool calls;
- one game-tool timeout, after which status remained healthy and another tool
  succeeded; and
- one transport error, deliberately caused by terminating the stdio GABS
  process solely to make it reread edited configuration.

Fourteen separate live-smoke runs add a second usage shape. All fourteen
started the workload, and thirteen connected during `games_start`. The
remaining run exceeded the bounded initial bridge wait and then two early
connect attempts while the game was still loading. Nine runs ended in `PASS`;
of the five `FAIL` outcomes, four had already connected and failed in the game
integration scenario under test rather than in GABS lifecycle. Successful
starts were often followed by a redundant `games_connect`, which correctly
replied that the game was already connected.

The audit produced these generic conclusions:

| Observed friction | Classification | V3 consequence |
| --- | --- | --- |
| A caller selected a misleading generic ID and launched the wrong configured installation | caller error aided by weak identity summaries | list/show/status/start expose concise identity discriminators; neither agents nor migration heuristics guess across different targets or modes |
| Two entries were exact launch duplicates, while another entry represented a genuinely different target/mode | legacy-config shape | the planner distinguishes exact deduplication, profile candidates, and separate identities instead of manufacturing redundant profiles |
| The same target was directly edited from an ordinary launch configuration into an isolated test context | direct profile use case | avoid destructive config mutation by keeping one game identity and selecting explicit profiles for repeatable args/env/cwd variants |
| Config edits required killing GABS, closing the MCP transport, using a temporary server, and finally restarting the client session | GABS config-reload deficiency plus host transport behavior | automatic atomic reload and visible revisions are release requirements, not optional polish |
| Five starts supplied the undeclared field `timeoutSeconds` and succeeded because it was silently ignored | handler validation deficiency | unknown or misspelled fields fail with structured path-aware errors |
| Slow bridge startup required status/connect reasoning even though the workload was valid | game/bridge latency; conservative GABS behavior was correct | preserve background attachment, but expose operation/workload/bridge phases, retry timing, and exact idempotent next actions |
| One graceful stop did not return within a minute | game/process behavior exposed an unbounded GABS interaction | every MCP lifecycle caller has a bounded wait result and a persisted operation that remains observable |
| A running external process lacked the managed bridge environment and could not be trusted | external process state; GABS diagnosis was correct | profile recovery requires positive evidence and never adopts the current default or a caller hint as fact |
| Search for a word present in every game-ID prefix overwhelmed relevant bridge results | GABS discovery relevance issue, independent of profiles | profile names never enter tool identity/search; local-name-centric ranked search is an adjacent follow-up, not issue-66 scope |

The evidence argues against a broad rewrite of the normal GABS workflow: nearly
all lifecycle and game calls succeeded. V3 instead strengthens the boundaries
where real use became ambiguous—identity selection, config freshness, strict
arguments, transition visibility, bounded lifecycle waits, and safe mapping.

## Product promise

After this change, a user or agent can:

- distinguish configured game identities, then discover the profiles and
  declared launch inputs for the selected game;
- start one named profile with a deterministic resolved launch context;
- ask for a declared startup variation such as `quickStart` without gaining a
  raw argument or environment escape hatch;
- observe, stop, or kill wrapped and detached launches through configured
  lifecycle hooks;
- edit configuration and use it on the next operation without restarting GABS
  or the MCP client;
- recover and operate an active launch after a GABS restart or after its
  original profile was edited or removed;
- map old single-entry or duplicated-entry configurations into profiles using
  a deterministic, non-writing plan; and
- receive a bounded, observable MCP lifecycle result even when launch, bridge
  attachment, or termination continues beyond the caller's wait budget, with
  the standalone-CLI commit safety exception reported explicitly.

GABS guarantees profile selection and deterministic transport of launch
context. It cannot guarantee filesystem, save, log, mod, or container
isolation if the configured launcher or game ignores that context. Public
wording must make that boundary explicit.

## Non-goals

- No game-specific configuration concept such as `dataDir`, `saveDir`, or
  `modList`.
- No arbitrary MCP-supplied arguments, environment variables, commands, or
  executable paths.
- No multiple concurrent instances beneath one game ID. Distinct simultaneous
  instances remain distinct canonical game IDs.
- No heuristic grouping or automatic deletion of existing game entries.
- No config rewrite as a side effect of start, status, connect, stop, or kill.
- No implicit shell parsing, tilde expansion, glob expansion, interpolation by
  a shell, or command substitution.
- No dynamic profile-specific MCP tools and no `tools/list` churn.
- No GABP wire-version change.
- No promise that a launch input was requested by a human. GABS can enforce
  that an input is declared and explicitly present in the call; agent guidance
  governs when an agent should choose to pass it.

## Core model and invariants

### Game identity

A game ID is the stable identity for:

- target and launch mode;
- GABP endpoint and `GABS_GAME_ID`;
- mirrored game-tool namespace and discovery identity;
- runtime directory and runtime snapshot;
- cross-session ownership and operation locking;
- the single-active-instance rule; and
- status, connect, stop, and kill routing.

Different targets, installations, launch modes, or effective `gabpMode` values
remain different game IDs. A profile never overrides identity. Derived
endpoint, namespace, runtime, and ownership identity follows the canonical game
ID; it is not an additional configured grouping field.

Profile names never prefix, rename, or otherwise participate in mirrored game
tool names or search. Changing profiles beneath one game ID must not churn the
public tool namespace.

### Profile

A profile is a named launch-context overlay. It may define:

- `description`;
- `args`;
- `env`;
- `unsetEnv`;
- `workingDir`; and
- complete per-hook `lifecycle.status`, `lifecycle.stop`, or `lifecycle.kill`
  replacements.

A profile may not define or override:

- `id` or `name`;
- `target` or `launchMode`;
- `gabpMode` or any derived bridge/runtime identity;
- `stopProcessName`; or
- GABS-managed endpoint, token, ownership, or runtime fields.

Game-level launch-context fields are the common base. Profiles add to or
override that base. Base arguments cannot be removed by a profile; therefore a
configuration author must keep only genuinely common arguments at game level.
The legacy mapping plan handles this conservatively by moving all existing
mutable launch context into an initial profile.

Exactly one profile, or the legacy unprofiled launch, may be active for a game
ID at once.

### Launch input

A launch input is a named, typed, configuration-declared input to launch
resolution. It is not a raw argument or environment API.

Launch inputs are lifecycle-identity-neutral by contract. They may alter what
an already identified workload does at startup, but may not choose the process,
container, wrapper instance, service, data root, or other identity that status,
stop, kill, or restart recovery must later reconstruct. Any variation needed
to locate or control the workload belongs in a named profile, whose lifecycle
spec and identity are snapshotted. This is the boundary that keeps transient
input values useful without persisting them as operational secrets.

Supported types are:

- `boolean`;
- `string`; and
- `integer`.

String inputs may declare `enum`. Integer inputs may declare `minimum` and
`maximum`. Inputs may list the profiles for which they are valid. They have no
implicit runtime defaults: an omitted input never changes a launch.

The name `launchInputs` is intentional. It describes bounded input to a
resolver and avoids suggesting a general-purpose "launch options" escape
hatch. Its constraints still use normal JSON-Schema vocabulary.

## Configuration schema

Profiles and lifecycle fields require top-level config version `1.1`. GABS
continues to accept existing version `1.0` files without changing their
behavior.

```json
{
  "version": "1.1",
  "games": {
    "adventure": {
      "id": "adventure",
      "name": "Adventure Game",
      "launchMode": "DirectPath",
      "target": "/opt/example/adventure",
      "args": ["--bridge"],
      "env": {
        "LOG_FORMAT": "json"
      },
      "unsetEnv": ["DEVELOPMENT_OVERRIDE"],
      "defaultProfile": "vanilla",
      "profiles": {
        "vanilla": {
          "description": "Normal isolated launch context",
          "args": ["--data-root", "/srv/adventure/vanilla"]
        },
        "combat-test": {
          "description": "Combat test launch context",
          "args": ["--data-root", "/srv/adventure/combat-test"],
          "env": {
            "CONTENT_SET": "combat"
          },
          "workingDir": "/srv/adventure/combat-test"
        }
      },
      "launchInputs": {
        "quickStart": {
          "description": "Skip menus and enter the configured quick-start path",
          "type": "boolean",
          "args": ["--quick-start"]
        },
        "scenario": {
          "description": "Select one configured startup scenario",
          "type": "string",
          "enum": ["arena", "tutorial"],
          "profiles": ["combat-test"],
          "args": ["--scenario", "${value}"],
          "env": {
            "START_SCENARIO": "${value}"
          }
        }
      },
      "lifecycle": {
        "status": {
          "command": "example-runtime",
          "args": ["is-running", "adventure-${profile}"],
          "timeoutSeconds": 5
        },
        "stop": {
          "command": "example-runtime",
          "args": ["stop", "adventure-${profile}"],
          "timeoutSeconds": 30,
          "verificationTimeoutSeconds": 15,
          "completionEvidence": "commandExit"
        },
        "kill": {
          "command": "example-runtime",
          "args": ["kill", "adventure-${profile}"],
          "timeoutSeconds": 10
        }
      }
    }
  }
}
```

All names, commands, paths, and values above are neutral examples. Public docs
and tests must use similarly neutral names.

### Version behavior

- Version `1.0` remains the legacy schema and may omit every new field.
- A historically accepted absent or empty version canonicalizes to legacy
  `1.0` with a warning. It does not silently opt into profile behavior.
- A file using `env`, `unsetEnv`, `profiles`, `defaultProfile`,
  `launchInputs`, `lifecycle`, or `timeouts.startup.preflightSeconds` must
  declare version `1.1`.
- New GABS versions reject unsupported future schema versions and reject new
  feature fields under `1.0`. The value of `1.1` is a strict contract for this
  and future binaries, not protection from already-released binaries.
- Existing GABS builds do not currently enforce the version field and may
  ignore unknown JSON fields. Consequently, a profile-enabled config must not
  be used after downgrading to a pre-profile GABS binary. This limitation must
  be prominent in release notes and diagnostics; it cannot be repaired solely
  by choosing a new version string.
- Version `1.1` is strictly validated. Unknown fields are errors. Legacy `1.0`
  compatibility issues that were historically accepted may remain warnings,
  except security-critical identity/path problems.
- Strict decoding also rejects duplicate JSON object keys; normal
  last-key-wins decoding is too easy to misread in launch configuration.

Both earlier drafts proposed leaving the schema at `1.0`. V3 intentionally
changes that decision because current decoding silently ignores unknown fields.
The bump makes profile-aware validation explicit going forward, while the
downgrade limitation above remains unavoidable for older binaries.

### Names and references

- Profile and launch-input names are case-sensitive and match
  `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`.
- A game may declare at most 128 profiles and 128 launch inputs; larger
  collections fail validation rather than creating unbounded discovery/probe
  work.
- Version-1.1/new game IDs match
  `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`. A path-safe version-1.0 ID outside that
  preferred grammar remains accepted with a migration warning.
- Under version `1.1`, the game map key must equal the contained game `id`.
  A legacy `1.0` mismatch remains readable with a warning and an unambiguous
  canonical-ID diagnostic.
- Introduce one shared safe-ID validator and apply it before any ID reaches a
  runtime/bridge path. Use it in config loading, CLI operations, MCP
  resolution, runtime/cache path construction, and runtime-directory scans.
- Every version rejects genuinely dangerous filesystem identities: empty,
  absolute, `.`/`..`, path separators, NUL, or any value whose cleaned resolved
  game directory escapes the configured GABS base directory.
- Canonical IDs are preferred for every operation. If backward-compatible
  target lookup remains, GABS collects every target match: exactly one may
  resolve, while multiple matches return `ambiguous_game_reference` with
  sorted candidate IDs. It never selects the first Go-map iteration result.
- `defaultProfile`, when present, must name an existing profile.
- In version 1.1, omitted `gabpMode` has the canonical effective value `local`;
  `local` is the only accepted value until another transport mode has an
  explicit protocol contract. Legacy version-1.0 values remain readable under
  their existing compatibility policy.
- A launch input's `profiles` entries must name existing profiles and contain
  no duplicates.
- Lists and diagnostic output are sorted deterministically.

### Profile selection

- No `profiles`: an omitted profile preserves the current unprofiled launch.
- No `profiles` plus a requested profile: return `profiles_not_configured`
  without launching.
- Profiles plus a valid requested profile: use it.
- Profiles plus no requested profile and a configured `defaultProfile`: use
  the default.
- Profiles plus no requested profile and no default: return
  `profile_required` with sorted candidates. This is a valid deliberate
  configuration, not a load error.
- An unknown requested profile returns `profile_not_found`, the default if
  present, and sorted candidates.

The default is a launch convenience only. It is never assumed to be the
currently active profile when runtime evidence is absent.

### Environment fields

`env` is a string-to-string map. `unsetEnv` is a list of keys to remove before
the layer's `env` map is applied.

- A key cannot appear in both `unsetEnv` and `env` in the same layer.
- Empty names, `=`/NUL in names, NUL in values, and duplicate names after
  platform case folding are rejected. `unsetEnv` likewise rejects duplicates
  and platform-equivalent duplicates.
- Keys under `GABS_` or `GABP_` are reserved and rejected in game, profile,
  launch-input, and lifecycle configuration.
- Reserved-prefix checks are ASCII case-insensitive on every platform.
- Environment keys are merged case-insensitively on Windows and according to
  platform semantics elsewhere.
- GABS does not expand `~`, `$NAME`, `%NAME%`, or shell expressions in paths or
  environment values.
- NUL is also rejected in argv elements, executable names, and working
  directories. Hook timeouts must be positive and within a documented upper
  bound.

### Launch-input bindings

Each launch input has a required non-empty `description`, a `type`, optional
constraints/applicability, and at least one `args` or `env` binding.

- A boolean input applies its bindings only when supplied as `true`; `false`
  is equivalent to omission. Boolean bindings may not contain `${value}`.
- A string or integer input substitutes its canonical string value for every
  `${value}` occurrence inside each configured argv element or environment
  value. At least one occurrence is required; otherwise the declaration should
  be a boolean input.
- Substitution never crosses argv boundaries and never invokes a shell. A value
  containing spaces or metacharacters remains literal data in one argument or
  environment value.
- Enum members are unique and match the declared type. Integer values are
  integral JSON numbers and must satisfy inclusive bounds.
- Input groups are applied in lexical input-name order, independent of JSON map
  order.
- If two simultaneously applicable inputs can write the same environment key,
  validation rejects the ambiguous configuration rather than relying on sort
  order to choose a winner.
- Input bindings cannot affect target, command, working directory, profile,
  lifecycle hooks, or GABP identity.
- Lifecycle placeholders cannot reference launch-input values. This keeps
  recovery snapshots independent of transient supplied values.
- Configuration authors must keep input-bound argv/env lifecycle-identity-
  neutral. If an input value would be required to distinguish the launched
  process, container, service, status target, or termination target, that
  variation must be a profile instead. GABS enforces the structural boundary
  above but cannot infer arbitrary executable or argument semantics.
- Launch-input values are not a secret store. They are never logged, persisted,
  or echoed in results, but they still travel through the calling transport.

## Deterministic launch resolution

A pure resolver accepts:

- one immutable config snapshot and its revision;
- one canonical game ID;
- an optional selected profile; and
- supplied declared launch-input values.

It produces:

- an immutable process launch specification;
- a resolved lifecycle snapshot;
- selected profile and applied input names;
- validation diagnostics; and
- the exact config revision used.

All maps and slices are deep-copied. Resolution has no process or filesystem
side effects.

### Argument order

1. game-level `args`;
2. selected-profile `args`; and
3. supplied launch-input arg groups in lexical input-name order.

### Environment order

1. convert the inherited environment to a map;
2. remove every inherited `GABS_*` and `GABP_*` key;
3. apply game `unsetEnv`, then game `env`;
4. apply profile `unsetEnv`, then profile `env`;
5. apply supplied launch-input `env` bindings in lexical name order; and
6. inject launch-mode/platform-required variables and GABS-managed variables
   last.

Managed launch variables are:

- `GABP_SERVER_PORT`;
- `GABP_TOKEN`;
- `GABS_GAME_ID`;
- `GABS_PROFILE_STATE=selected|unprofiled` for schema-1.1 launches;
- `GABS_PROFILE` when a profile is selected; and
- `GABS_BRIDGE_PATH` only as endpoint-cache/debug metadata.

`GABS_PROFILE_STATE` is deliberately positive attribution: schema-1.1 launches
always set it, while legacy schema-1.0 launches do not gain a new environment
variable. `selected` requires `GABS_PROFILE`; `unprofiled` requires that
`GABS_PROFILE` be absent. The marker is diagnostic/recovery metadata, not a
new game-side bridge connection requirement.

Existing launch-mode/platform-required variables, including the managed store
identity variables used by `SteamManaged` and Windows `SystemRoot`/`WINDIR`
compatibility, remain in the final managed layer. Game/profile/input config
cannot override them.

The live game-side bridge contract remains
`GABP_SERVER_PORT`/`GABP_TOKEN`/`GABS_GAME_ID`. Neither a game-side bridge nor
an agent recovery flow reads `runtime.json`, and `GABS_BRIDGE_PATH` is not live
connection truth. A bridge may report `GABS_PROFILE_STATE`/`GABS_PROFILE` as
observed launch context but need not consume them to serve GABP.

### Working directory

Use profile `workingDir` when non-empty, otherwise game `workingDir`. Paths are
literal inputs: there is no home/environment expansion, while relative-path
base resolution follows the next section. Validation and doctor output clearly
report nonexistent directories.

### Path and target normalization

The immutable config snapshot includes the absolute directory containing the
config file. One shared resolver helper is used by execution, doctor, and the
mapping planner:

- For version 1.1, relative game/profile/hook working directories resolve
  against that config directory, then use platform `filepath.Clean` semantics.
- For `DirectPath` and `CustomCommand`, a target containing a path separator is
  path-like: an absolute value is cleaned, and a relative value resolves
  against the config directory. A separator-free command name resolves once
  through the pinned sanitized `PATH`; failure is a validation/doctor error.
  Execution uses the resulting absolute executable path.
- Targets for ID/URL-based or managed-resolver launch modes are opaque validated
  strings. The planner does not reinterpret them as paths or numeric values.
- Effective paths compare with separator/volume normalization and ASCII
  case-folding on Windows. They compare byte-for-byte after cleaning on every
  other platform, including macOS; GABS does not guess a volume's case
  sensitivity.
- Resolution never calls `EvalSymlinks`. Two different paths to the same inode
  are not mechanically equivalent unless the user explicitly normalizes them.

Version 1.0 keeps its historical execution semantics. A profile plan that
would upgrade a relative legacy target or working directory to 1.1 cannot
claim equivalence from a different process working directory; it returns a
normalization blocker and asks the user to make the legacy path absolute first.
Lexically identical relative values may still be recognized for a
no-schema-bump exact-deduplication plan.

### GABS-side propagation-capable launch modes

Profiles and launch inputs are allowed only when the launch mode can pass the
resolved process arguments, environment, and working directory to the
configured/resolved executable. `DirectPath`, `SteamManaged`, and
`CustomCommand` satisfy that GABS-side contract in the current architecture.
GABS cannot guarantee that a downstream launcher or wrapper preserves the
context. `games_doctor` reports static GABS-side capability, while
`games_status` reports observed final-process bridge/profile-state environment
where the platform permits inspection, including whether the positive
`GABS_PROFILE_STATE` marker survived propagation. Missing values downstream
are runtime diagnostics, not evidence that resolver ordering changed.

URL-only launcher modes such as `SteamAppId` and `EpicAppId` reject profiles
and launch inputs entirely. Allowing a lifecycle-only "profile" while failing
to deliver `GABS_PROFILE` to the game would make the product promise ambiguous.
Game-level lifecycle hooks remain valid for those modes.

## Structured lifecycle hooks

Lifecycle hooks are exact executable-plus-argv specifications, never shell
strings.

Each `status`, `stop`, or `kill` hook supports:

- `command` (required);
- `args`;
- `workingDir`;
- `env` and `unsetEnv`;
- `inheritLaunchEnv` (default `false`);
- `timeoutSeconds`;
- `runningExitCodes` and `stoppedExitCodes` for status; and
- `successExitCodes` for stop/kill;
- `verificationTimeoutSeconds` for stop/kill; and
- `completionEvidence: "commandExit"|"verify"` for stop/kill.

Defaults are:

- status timeout: 5 seconds;
- stop timeout: 30 seconds;
- kill timeout: 10 seconds;
- stop/kill post-action verification timeout: 15 seconds;
- status running exit codes: `[0]`;
- status stopped exit codes: `[1]`; and
- stop/kill success exit codes: `[0]`; and
- stop/kill completion evidence: `commandExit`.

Status-hook timeouts are integral seconds from 1 through 60. Stop/kill-hook
timeouts are integral seconds from 1 through 3600.
`verificationTimeoutSeconds` is integral from 1 through 600. Boolean, string,
fractional, zero, negative, and over-limit values are validation errors. The
tighter status limit keeps profile-exclusion and passive observation budgets
finite even for the maximum supported profile set; lifecycle actions may need
substantially longer.

Running and stopped sets must be non-empty, duplicate-free, and disjoint. Any
unclassified status exit code is `unknown`, as are timeout, cancellation, and
execution failure. This preserves v2's simple defaults without misclassifying
real failures as stopped; uncommon tools can use explicit code sets or a
wrapper.

For stop/kill, a success exit means `actionSucceeded: true`, not automatically
that termination was observed. With default `completionEvidence: commandExit`,
success becomes provisional stopped evidence only when no status hook exists
and no stronger live GABP/workload/process evidence remains after the
verification window. This makes the issue sender's stop-only wrapped/container
case usable while refusing to discard contradictory live state. With
`completionEvidence: verify`, command exit never proves termination by itself;
a status hook or strong process evidence must do so. A failed/timed-out action
is never positive termination evidence, although fresh evidence may still show
that its partial side effect stopped the workload.

### Command execution

- `command` is a literal absolute path or an executable resolved through the
  GABS process `PATH`. It does not support placeholders. Before an active
  launch is committed, GABS resolves a PATH-based command to an absolute path
  and stores that path in the runtime snapshot so restart recovery does not
  depend on a later process having the same `PATH`.
- `${gameId}`, compatibility alias `${id}`, and `${profile}` may appear in
  hook args, working directory, and environment values.
- `${profile}` is invalid where no concrete profile is available. The default
  profile is never substituted merely because active identity is unknown.
- Unknown placeholders are config-validation errors.
- A profile hook replaces the complete same-named game hook. Hook objects are
  not field-by-field merged.
- An explicit hook working directory wins; otherwise the effective profile/game
  launch working directory is used; otherwise the hook inherits the GABS
  process working directory. The selected value is resolved and snapshotted
  with the active launch.
- Hook environment order is sanitized inherited OS environment (with inherited
  managed keys removed) -> optional resolved game/profile env when
  `inheritLaunchEnv: true` -> hook `unsetEnv` -> hook `env` ->
  `GABS_GAME_ID`/known `GABS_PROFILE`, plus `GABS_OPERATION_ID` for stop/kill.
  It never inherits launch-input bindings. The operation ID is a diagnostic/
  recovery correlation value, not authority for the hook to call GABS.
- Lifecycle hooks do not receive `GABP_TOKEN` or `GABP_SERVER_PORT`. They have
  only the authority required to identify, inspect, or stop the selected
  launch.
- Stdout and stderr are captured up to 16 KiB per stream with byte counts and a
  truncation marker. Normal MCP results and logs do not expose raw hook argv,
  env, stdout, or stderr because there is no reliable way to guess which text
  is sensitive. They expose command basename, exit code, duration, timeout,
  byte counts, and stable diagnostics. An explicit local CLI verbose mode may
  print captured output.
- Timeout cancellation terminates the hook process tree where the platform
  permits it. For stop/kill, failure to prove that tree reaped sets the
  persistent action-process hazard; workload evidence alone cannot clear it.
  An unreaped observational status probe remains an `unknown` probe failure
  and is reported separately, never mistaken for a lifecycle action.
- No external hook executes while the global MCP server mutex is held.

### Resolution order

For each hook independently:

1. the selected profile's complete hook override;
2. the game-level hook; and
3. existing built-in PID/process fallback when no hook exists.

`kill` never silently substitutes `stop`. If no force-capable hook or tracked
process action exists, GABS returns a precise unsupported result.

`stopProcessName` remains a legacy fallback. A known, fingerprinted PID or
configured lifecycle hook is preferred because process-name stopping can match
unrelated processes. GABS warns when multiple configured games share a process
name and never uses process name when stronger identity is available.

Process fingerprints are best-effort platform evidence: PID plus process start
time and executable identity where readable. Persist them immediately after
`cmd.Start`, before bridge waits or other asynchronous work. A mismatch always
forbids signalling that PID. If identity is unreadable after restart, degrade
to status-hook/GABP/legacy evidence or `unknown`; do not treat PID existence
alone as proof. Fingerprint unavailability is not fatal when a status hook can
manage liveness, and URL-launch modes are not assumed to expose a reliable
workload PID.

## Liveness and active-profile state model

The current implementation assumes that the launcher process is the game. That
does not hold for detached wrappers or containers. V3 introduces one liveness
oracle used by startup, GABP waiting, status, recovery, stop, and kill.

### Evidence

GABS records independent evidence from:

- a live GABP connection;
- a configured status hook;
- the launcher PID returned by `cmd.Start`;
- a verified workload PID plus process birth/executable fingerprint, when the
  platform and launch mode can identify one;
- `GABS_PROFILE_STATE` and `GABS_PROFILE` read from the verified workload
  process environment;
- legacy `stopProcessName`; and
- the persisted active-launch snapshot and ownership lease.

The liveness oracle produces only workload state `running`, `stopped`,
`unknown`, or `conflicted`. Runtime occupancy is a separate consequence.

The deterministic precedence is:

| Status hook | Other evidence | `workloadState` | Runtime consequence |
| --- | --- | --- | --- |
| running | any launcher-PID state | `running` | preserve a claim and block start |
| stopped | live GABP or verified live workload PID | `conflicted` after the relevant settling deadline | preserve occupied claim |
| stopped | no strong live workload evidence | `stopped` | release only after GABS-started launcher tree is reaped |
| unknown/error | live GABP or verified live workload PID | `running` with degraded diagnostics | preserve a claim and block start |
| unknown/error | no strong live workload evidence | `unknown` | preserve a claim; pre-start remains blocked even without one |
| absent | live GABP or verified live workload PID | `running` | preserve a claim and block start |
| absent | verified built-in foreground PID exited and no contrary evidence | `stopped` | reconcile to no claim |
| absent | one unique process-name match with no configured collision | `running` | preserve a claim and block start |
| absent | no process-name match and no runtime claim | `stopped` | remain without a claim |
| absent | multiple/colliding matches, lookup failure, or an unsupported active claim | `unknown` | preserve a claim and block start |

When a status hook is configured, it defines managed workload liveness. The
launcher PID is wrapper evidence only and cannot create a permanent conflict
with a definitive hook result. A live GABP connection remains stronger
contradictory evidence because it proves the bridge is still serving.

Without a hook, the launched PID is treated as the workload only for a launch
mode whose built-in lifecycle makes that identity valid. Merely fingerprinting
a wrapper does not turn it into the workload.

A verified process environment can recover missing launch identity only from
the complete positive attribution tuple. A selected profile requires
`GABS_PROFILE_STATE=selected`, canonical `GABS_GAME_ID`, and the selected
`GABS_PROFILE`; an unprofiled launch requires the separate predicate below. A
mismatch with a trusted runtime snapshot is `conflicted`; an arbitrary
same-name process is never trusted without process-identity proof.

Hook timeout, unclassified exit, or execution failure is `unknown`. `unknown`
preserves an existing runtime claim and never authorizes a new launch. GABS
cleans active state only after termination is positively verified.

The phrase "after the relevant settling deadline" applies only to an active
transition: process-start deadline during `starting`, and the distinct
post-stop/post-kill verification deadline during termination. Passive
`games_status`, `games_connect`, pre-start discovery, and recovery report
contradictory strong evidence as `conflicted` immediately and never clean it up
as a side effect.

### Where the status hook applies

A resolved status hook participates in:

- pre-start duplicate detection across every configured profile;
- initial process-start verification;
- synchronous and background GABP connection waiting;
- detection of stale shared runtime state;
- `games_status` and `games_connect` diagnostics;
- post-stop verification;
- post-kill verification;
- CLI status; and
- recovery after GABS or the original launcher exits.

If a launch wrapper exits but the status hook reports running, startup and GABP
waiting continue. The wrapper exit alone does not erase the launch.

During `starting`, an early status `stopped` or `unknown` is a settling result,
not immediate cleanup. GABS polls with bounded backoff until the configured
process-start deadline. `running` commits the launch; a final definitive
`stopped` fails and cleans the attempted start; a final `unknown` leaves an
`occupied_unverified` runtime claim with outcome `startup_unverified` and
recovery actions so another process cannot be started blindly.

Before any hook-stopped result releases the game ID, GABS terminates and reaps
the still-live launcher process tree that it started, using its fingerprinted
identity. If that cannot be verified, the ID remains occupied/unknown: a live
wrapper or supervisor might create the workload later. The status-hook
`stopped` contract proves workload absence, not that an independently live
launcher has lost the ability to restart it.

### Discovering an externally active profile

Only a trusted `active` or `recovered` runtime snapshot supplies authoritative
launch identity through either explicit `profileState: unprofiled` or
`profileState: selected` plus `selectedProfile`; GABS never replaces it with
the current default. `snapshotKind` by itself proves no identity. An
`occupancy_only` snapshot may carry a separately labeled
`observedActiveProfile` when fresh trusted evidence establishes one, but that
observation is not an active-launch/recovery snapshot and cannot authorize a
termination action.

When no authoritative `selectedProfile` exists and status hooks depend on
`${profile}`, GABS probes configured profiles with bounded concurrency:

- no running profiles: stopped if all probes are definitive, otherwise
  unknown;
- exactly one running profile: report that externally observed profile;
- more than one running profile: `multiple_profiles_running`/`conflicted`;
- a game-level non-profile-sensitive hook may prove running but leaves
  `activeProfile` unknown.

Use one shared `trustedActiveProfileEvidence` predicate in status, connect,
recover, stop, and kill. It succeeds only when exactly one profile is
established by either:

- a `running` status hook whose resolved identity is both profile-specific and
  canonical-game-specific. Referencing both `${gameId}`/`${id}` and
  `${profile}` is sufficient; otherwise validation/doctor must prove the
  configured command/args/working-directory/environment targeting spec is
  unique across every configured game/profile with a colliding target/process
  identity. Automatically injected managed environment does not count as proof
  because the hook may ignore it; or
- a fingerprint-verified workload process whose inspectable environment
  positively matches canonical `GABS_GAME_ID`,
  `GABS_PROFILE_STATE=selected`, and the selected `GABS_PROFILE`. Inability to
  inspect any variable is unknown, and a target/process collision without the
  complete matching tuple is never attributed.

Every other configured profile for that game must also be definitively stopped
or otherwise definitively excluded. Any unprobed, unknown, running, conflicted,
or cross-game identity-colliding status-hook competitor makes hook-based
uniqueness unproven; the exact matching game-ID environment branch may
disambiguate the latter. A caller-supplied profile may prioritize probe order
but cannot omit the exclusion probes and never contributes evidence itself.

For a configured game with no profiles, the parallel
`trustedActiveUnprofiledEvidence` predicate requires one
fingerprint-verified target/process match with no configured collision whose
inspectable environment positively matches canonical `GABS_GAME_ID` and
`GABS_PROFILE_STATE=unprofiled`, with `GABS_PROFILE` absent as a consistency
check. Absence of `GABS_PROFILE` without the positive state marker is not
evidence: a wrapper may have dropped it, and legacy schema-1.0 launches never
received the marker. Inability to inspect any required environment fact is
unknown. A game-level status hook or live GABP session may prove occupancy or
liveness, but `GABS_GAME_ID` alone cannot distinguish an old profiled workload
after config changed to no profiles and therefore cannot establish unprofiled
launch context. Unknown/conflicted evidence, multiple matches, or a
process-name/target collision fails the predicate. A future protocol-level
launch-context assertion could provide equivalent positive evidence, but v3
does not infer it. The predicate reconstructs explicit
`profileState: unprofiled`; it never invents a profile or borrows a default.
The shared `trustedActiveLaunchEvidence` predicate selects this rule when the
game has no profiles and `trustedActiveProfileEvidence` otherwise.

Start, stop, and kill refuse any operation that would require guessing an
active profile. `games_stop` and `games_kill` normally need no profile because
they use the persisted launch snapshot; an explicit recovery profile is only a
probe/selection hint when the snapshot is unavailable and must satisfy
`trustedActiveProfileEvidence` before stop/kill can act.

Status-all operations run independent probes with bounded concurrency. A slow
hook for one game must not serialize every other game or block MCP discovery.

## Lifecycle operation state machine

MCP, CLI, and multiple GABS processes must not race start/stop/kill operations.
Use the existing ownership model plus a per-game cross-process operation lock
and expose orthogonal state domains rather than overloading one `status`
string:

- `runtimePhase`: `starting`, `active`, `stopping`, `killing`, or
  `occupied_unverified`; absence of a runtime claim means only "no managed
  claim" and never proves that the workload is stopped;
- `operationKind`: `start`, `connect`, `stop`, `kill`, or `recover`;
- `operationState`: `accepted`, `executing`, `verifying`, `completed`,
  `failed`, `timed_out`, or `cancelled`;
- `workloadState`: `not_started`, `starting`, `running`, `stopped`, `unknown`,
  or `conflicted`; the lifecycle manager synthesizes the first two before a
  definitive observation, while the liveness oracle produces only the final
  four;
- `bridgeState`: `not_expected`, `idle`, `waiting`, `connected`,
  `disconnected`, or `unavailable`; and
- `ownershipState`: `unowned`, `owned_by_caller`, `owned_by_other_active`, or
  `owned_by_other_expired`.

The persisted runtime-claim transitions are:

    no claim -> starting -> active -> stopping -> no claim
                              \-----> killing  -> no claim
       |           |              |       |
       +-----------+--------------+-------+-> occupied_unverified

Fresh evidence reconciles `occupied_unverified` to `active` when the workload
is definitively running or to no claim when it is definitively stopped and no
action-process hazard remains. It remains occupied for `unknown` or
`conflicted` evidence or any live/unknown action hazard. `unknown` and
`conflicted` are workload observations, never operation states or cleanup
states.

The domains have explicit sources rather than all being described as
"persisted":

| Domain | Source of truth |
| --- | --- |
| runtime phase/generation | persisted current runtime claim |
| operation state | current operation stored with the runtime claim; terminal history journal |
| workload state | lifecycle-synthesized `not_started`/`starting` or fresh four-state liveness observation, always with source/`observedAt`; optionally snapshotted into a terminal record |
| bridge state | live controller plus last-known observation; persisted `connected` downgrades to `disconnected` after restart, while never-attempted expected attachment is `idle` |
| ownership state | derived for the current GABS/CLI instance from the persisted owner lease |

Here "caller" means the current GABS or CLI instance ID, not the MCP user.
Lease expiry permits locked evidence reconciliation; it is never proof that the
workload stopped. Passive status may report no runtime claim plus a running or
unknown workload. Under the operation lock, pre-start reconciliation may
persist `occupied_unverified` to prevent a cross-process duplicate, but a
read-only status call does not create that claim.

Operation state is independent of runtime phase. For example, a start may be
`verifying` while runtime phase is `active`, workload state is `running`, and
bridge state is `waiting`. A stop operation may become terminal `timed_out`
while runtime phase becomes `active` after verified-running evidence or
`occupied_unverified` after unknown/conflicted evidence. Every result uses the
same enums and includes an outcome code for finer detail; no handler invents a
combined free-form status as machine state.

Legal operation progression is:

    accepted -> executing -> verifying -> completed | failed | timed_out | cancelled

An operation may skip an inapplicable middle phase, but never moves out of a
terminal state. `cancelled` means manager-side supersession, forced forgetting,
or shutdown/dead-executor reconciliation; post-acceptance caller/transport
cancellation never sets it. Outside the non-supersedable workload/action
creation commits defined below, stop/kill atomically terminalizes an
outstanding start/connect as `cancelled` with `superseded_by_stop` or
`superseded_by_kill`, advances the generation, and installs the termination
operation. A second equivalent
stop/kill observes or joins the existing
termination operation instead of replaying a possibly non-idempotent action;
a stop never supersedes an in-progress kill. Kill may explicitly escalate an
in-progress stop in `recovery` only after cancelling/reaping its observational
probe tree and terminalizing that stop `cancelled`/`superseded_by_kill`. Once a
stop action commit has begun, escalation additionally requires GABS to cancel
and reap the managed stop-hook process tree, mark that stop cancelled, and
refresh liveness. If a probe/action cannot be safely reaped or its invocation
is `prepared|may_have_started`, kill reports the current operation without
starting a concurrent hook. Other conflicting termination requests report the
current operation and an exact safe next step.

`operationPhase` is kind-specific and closed: start uses
`preflight|spawn_commit|process_verification|attachment`; connect uses
`attachment`; stop/kill use `recovery|action|verification`; and recover uses
`evidence|reconcile`. `operationState` describes progress/terminality, while
the phase identifies which pinned budget and restart rule applies.

The operation lock is a separate, stable, never-renamed `operation.lock` file;
atomic replacement of `runtime.json` is not a lock. One tested cross-platform
abstraction holds a nonblocking OS advisory exclusive lock on that file
(`flock`-class behavior on Unix and `LockFileEx`-class behavior on Windows),
combined with a per-game in-process mutex. All GABS/CLI lifecycle paths use the
abstraction. OS handle release recovers crashes without a racy
read-delete-create protocol; contenders never delete or replace a lock based on
stale metadata.

While holding the OS lock, write informational operation ID/generation, action,
owner PID plus fingerprint, GABS/CLI instance ID, acquisition time, and
deadline for diagnostics. The metadata is not the mutual-exclusion primitive.
Acquisition observes a context deadline and returns the recorded owner/action
when busy. Tests include two simultaneous post-crash contenders and prove only
one can acquire while neither can remove the winner's generation.

The active runtime-owner lease and the short-lived operation lock serve
different purposes. Start/connect/stop/kill honor a foreign active owner lease.
Connect/stop/kill may override it only with explicit `forceTakeover`/
`--force-takeover`, reported in structured results. Operation deadlines extend
or renew the owner lease so a valid long hook cannot be stolen midway. An
expired foreign lease permits locked reconciliation without force; it does not
permit assuming stopped. A live foreign stop/kill is observed or joined and is
never replayed merely because controller ownership changes. Force takeover of
start/connect fences the old executor and terminalizes its operation before a
new publication can win.

Every start/connect continuation carries the operation generation. Beginning
stop/kill cancels outstanding startup/connect contexts and increments the
persisted runtime generation. Before every asynchronous publication, the
goroutine reacquires the narrow operation/state lock and compares its token to
the current persisted generation—not only an in-memory value. The generation
is recorded in both the runtime claim and operation journal; the journal's
newest generation remains authoritative when runtime has been removed.
Status/recovery cleanup uses the same serialized reconciliation path. A stale
callback from a different, force-forgotten, or force-taken-over GABS process
can never repopulate bridge state after termination.

For every operation:

1. acquire an immutable config snapshot under the global server mutex, release
   that mutex, then acquire the per-game in-process mutex and advisory lock;
2. read current runtime/journal evidence and apply join/supersession rules;
3. pin the config or active-launch snapshot needed by the operation;
4. atomically persist the runtime phase, generation, and current operation. A
   start stores its requested/resolved context only as `attemptedLaunch`, not
   as an active/recovered launch snapshot;
5. for start, persist `spawnState: preflight`, release the per-game locks, run
   duplicate-detection/profile-exclusion probes under the preflight budget,
   then reacquire and revalidate generation/operation ID. Definitive stopped
   evidence advances to `prepared`; running yields operation `completed`,
   outcome `already_running`, `runtimePhase: active`, and an occupancy-only
   record; definitive conflict or a completed probe plan with execution or
   classification failures yields operation `failed`, outcome
   `preflight_liveness_unverified`; unknown/unprobed evidence caused by phase-
   deadline exhaustion yields operation `timed_out`, outcome
   `preflight_timed_out`. Both uncertain results retain an occupancy-only
   `runtimePhase: occupied_unverified` record and never spawn;
6. without releasing the locks after `prepared`, enter the non-supersedable
   spawn commit described below. Non-start operations release the per-game
   locks before status/recovery probes, network, sleep, or polling waits, then
   reacquire them for the short termination-action commit described below;
7. execute or observe the remaining process action/hook under its pinned
   deadline, never holding the locks while waiting for the child action to
   exit;
8. reacquire the per-game locks before every publication, verify that the
   persisted generation/operation ID still matches, then release them again;
9. verify resulting liveness outside the locks; and
10. reacquire the per-game locks to terminalize/reconcile state atomically.

The advisory lock serializes state transitions, not the full external action.
The exceptions are short process/action-creation commits whose side effects
cannot be undone by generation fencing. After the preflight transition, start
keeps the per-game mutex/advisory lock, invokes the deadline-aware spawn
abstraction, and immediately persists either `spawnState: spawned` plus
PID/birth/executable fingerprint and atomically promotes `attemptedLaunch` to
the trusted active-launch snapshot, or persists `spawnState: failed` before
releasing the locks. No liveness wait or GABP work occurs inside this critical
phase. Stop, kill, takeover, recovery, and force-forget may wait for or report
this phase but cannot supersede it, remove runtime, or claim termination. Once
PID/failure is durable, normal supersession/generation rules apply.

Stop/kill action invocation uses the same commit principle and a persisted
`actionInvocationState`:

    not_started -> prepared -> started -> finished
                      |    \-> failed
                      +-- executor lost --> may_have_started

Immediately before invoking a configured hook or built-in termination action,
GABS persists `prepared` under the per-game lock. It keeps the lock only while
the deadline-aware action abstraction starts the hook or issues the built-in
side effect, then immediately persists `started` plus the hook PID/fingerprint
or built-in target/evidence, or `failed` when invocation definitively did not
occur. It releases the lock before waiting for hook completion or workload
convergence. A crash that leaves durable `prepared` is genuinely ambiguous and
is reported/reconciled as `may_have_started`; recovery never invokes that
action again. Stop, kill, takeover, force-forget, and escalation cannot pass an
unresolved action commit.

Public `actionStarted` and `actionSucceeded` are nullable facts, accompanied by
`actionInvocationState`. `actionStarted` is false for `not_started` or a
definitive invocation failure, true for `started|finished`, and unknown/null
for orphaned `prepared`/`may_have_started`. `actionSucceeded` remains
unknown/null until a classified action result exists. This represents the
crash window honestly instead of manufacturing a boolean.

Runtime also carries orthogonal
`actionProcessHazard: clear|live|presence_unknown`. A started hook remains
`live` until its fingerprinted process tree is positively exited/reaped; an
orphaned external-hook `prepared` commit or a hook action tree that cannot be
identified/reaped is `presence_unknown`. Workload-stopped evidence never
clears this hazard: an old stop hook could otherwise terminate a newly started
workload later. While the hazard is not `clear`, GABS preserves an occupied
claim and blocks start, new stop/kill actions, cleanup, and automatic profile
recovery. Normal recovery may clear it only through positive hook-tree
absence/reap evidence; explicit local force-forget may override it only after
displaying this exact risk. A built-in PID/signal action creates no separate
action process tree, so its hazard remains `clear` even when a crash leaves its
invocation state `may_have_started`; this says nothing about whether the
side effect occurred or workload termination was verified.

Positive hook-tree evidence may come from the persisted PID/birth/executable
fingerprint, a platform job/process-group identity, or a uniquely matched
`GABS_OPERATION_ID` environment tag where process inspection supports it. The
action abstraction records every available locator before releasing its commit
lock. Lack of such platform evidence is not treated as absence; the hazard
remains `presence_unknown` and the supported escape hatch is explicit local
force-forget.

The workload-spawn abstraction is driven by one absolute pinned
`processStartDeadline`, established immediately before process creation and
shared by `spawn_commit` and `process_verification`; verification receives
only the remainder and never starts a fresh process-start budget.

If the platform cannot interrupt an in-flight workload or action invocation
primitive safely, caller cancellation detaches but GABS retains the
lock/occupied claim until the primitive returns and PID/failure is committed;
it never releases the lock on a timer and risks a late unmanaged process or
unrecorded lifecycle action. At the caller/phase budget, GABS returns
`spawn_commit_pending` or `action_commit_pending` when a response channel
remains, while contenders return their bounded `operation_locked`/pending
result. These commit windows are the only permitted internal deadline
overruns, because falsely terminalizing them would be less safe than retaining
occupancy. Crash recovery from
`spawnState: prepared` probes trusted strong workload evidence. Running evidence
may recover the launch. Workload-stopped evidence alone is insufficient,
because an unidentified launcher/supervisor might still create it. Cleanup
requires positive spawn-side-effect absence proof from the spawn
abstraction/platform; without that proof it remains `occupied_unverified`
until supported recovery or explicit force-forget. Tests inject
stop/kill/forget and crashes immediately before, during, and after spawn
publication.

After spawn commit, stop/kill can supersede slow process verification or bridge
attachment, and generation fencing prevents a late callback from publishing
stale bridge or runtime state.

An occupancy-only preflight result has `snapshotKind: occupancy_only`. It has
no authoritative `selectedProfile`; fresh `trustedActiveProfileEvidence` may
populate a separately labeled `observedActiveProfile` plus provenance and
observation time. Applied launch-input names are unknown/empty. The requested
profile/revision/input names may remain only under redacted `attemptedLaunch`
diagnostics. Neither an observed profile nor attempted status/stop/kill specs
constitutes an active recovery snapshot or termination authority. Later
stop/kill must use the normal trusted recovery transition, exactly as if no
launch snapshot existed.

When stop/kill is accepted without a trusted active/recovered snapshot,
including when it supersedes `preflight`, it first persists its own
`operationPhase: recovery`, `runtimePhase: stopping|killing`, immutable current
config provenance, and pinned recovery budget under the new generation. That
generation fence makes the old preflight incapable of spawning. The recovery
phase owns the termination operation ID; it is not an unjournaled nested
`games_recover` call and it never uses `attemptedLaunch` hooks.

Because the active profile is not known at acceptance, the same immutable
config snapshot resolves every candidate profile/unprofiled lifecycle budget
without executing it. The operation pins a conservative hard-deadline
allocation using the largest candidate action timeout plus the largest
candidate verification timeout, independently, in addition to recovery and
reconciliation. After recovery selects one identity, its actual action and
verification phase deadlines use only that identity's smaller/equal budgets;
unused conservative slack is never reassigned. If no candidate has a valid
action for the requested stop/kill kind, validation fails before accepting the
termination operation. If only some candidates do, acceptance remains possible
but candidate support never substitutes for the identity eventually
recovered.

Recovery probes run outside the lock through the same
`trustedActiveLaunchEvidence` logic as `games_recover`:

- uniquely trusted running identity with a valid requested action atomically
  creates a `recovered` snapshot with
  `appliedLaunchInputsState: unavailable`, pins that identity's lifecycle
  action, and advances the same operation to `action`;
- uniquely trusted running identity without that requested action atomically
  retains `snapshotKind: occupancy_only`, records only the trusted observed
  identity/evidence (`observedActiveProfile` where applicable), and
  terminalizes `failed` with `recovered_identity_action_unsupported`,
  `actionStarted: false`, hazard `clear`, and no side effect. It preserves the
  active claim, grants no termination authority, and never borrows another
  candidate's hook. After config repair/reload, a later call reruns trusted
  recovery against the fresh config rather than being trapped behind an
  unusable recovered snapshot;
- definitive stopped evidence completes the termination operation without an
  action as `termination_observed_without_action` and safely removes its claim;
- definitive conflict or a completed evidence plan with execution/
  classification failures fails as `recovery_required`, preserves occupancy,
  and never starts an action; and
- unknown/unprobed evidence at the recovery deadline times out as
  `recovery_timed_out`, preserves `occupied_unverified`, and never starts an
  action.

Thus a stop that cancels a pending preflight cannot launch later and cannot
stop an unrelated workload using the requested profile's hook. A caller wait
may expire during recovery, but the accepted termination operation remains
observable and continues only to its pinned internal deadline.

### Deadline contract

All public durations are integral seconds. Budget values and the operation
`hardDeadline` are pinned at acceptance and never change after config reload.
Each later `phaseDeadline` is derived when that phase begins from its pinned
budget and cannot exceed the hard deadline, except that start's
`spawn_commit` and `process_verification` deliberately reuse the one absolute
`processStartDeadline` established before spawn. The normative budgets are:

| Budget | Range/default | Starts | Meaning |
| --- | --- | --- | --- |
| advisory-lock acquisition | fixed maximum 5s or shorter remaining caller wait | handler entry | pre-acceptance only; expiry returns `operation_locked` with no action |
| schema-1.1 `timeouts.startup.preflightSeconds` | 1..1200, omitted derives `max(10, requiredProbeSeconds)`, concurrency 8 | accepted start preflight | internal duplicate/profile-exclusion evidence |
| schema-1.1 `timeouts.startup.processStartSeconds` | 1..600, default 10s | immediately before process creation | one absolute budget shared by workload spawn and process/status start verification |
| schema-1.1 `timeouts.startup.gabpConnectSeconds` | 1..3600, default 60s | after workload start commits | default internal start attachment budget |
| public `games_start.timeout` | 1..3600; omitted uses config | after workload start commits | per-call internal start attachment override |
| `games_connect.timeout` | 1..600, default 15s | caller wait at handler entry; internal attachment at acceptance | one numeric budget, with caller time already spent on pre-acceptance locking not restored |
| status-hook `timeoutSeconds` | 1..60, default 5s | hook spawn | internal observational hook process-tree lifetime |
| stop/kill-hook `timeoutSeconds` | 1..3600; stop 30s, kill 10s defaults | hook spawn | internal lifecycle-action process-tree lifetime |
| stop/kill `verificationTimeoutSeconds` | 1..600, default 15s | action finishes/fails/times out | internal post-action liveness convergence |
| embedded stop/kill recovery | 1..1200, derived `max(20, requiredProbeSeconds)` when no trusted snapshot; otherwise 0 | termination acceptance | profile/unprofiled identity evidence before any action |
| MCP stop/kill `timeout` | 1..600, default 20s | handler entry | caller wait, including lock/recovery/action/verification time |
| standalone CLI stop/kill wait | exact internal operation hard deadline | termination acceptance | remains resident to a terminal result; no intentional pending return |
| MCP recover `timeout` | 1..1200, default 20s | handler entry | caller/evidence budget; pending reconciliation remains queryable; maximum covers the largest valid exclusion plan |
| standalone CLI recover `--timeout` | 1..1200, default 20s | accepted evidence phase | evidence budget followed by at most 1s reconciliation; CLI returns a terminal result |
| one-game passive status | fixed 20s | handler entry | total observational probe budget |
| status-all | fixed 30s, concurrency 8 | handler entry | total observational budget; unfinished games return `unknown`/partial evidence |
| reconciliation grace | fixed 1s | internal phase deadline | durable terminal publication only; never starts/replays an action |

Schema 1.1 allows at most 128 profiles per game and runs at most eight probes
concurrently. Validation first builds the deterministic exclusion-probe plan.
For its `N` probes, `requiredProbeSeconds` is
`ceil(N / 8) * (maxProbeTimeoutSeconds + 1)`; the extra second per wave covers
bounded spawn/reap/scheduling overhead. A status probe contributes its
configured timeout (at most 60 seconds), while a built-in process observation
contributes one second. A non-profile-sensitive game-level status hook is one
probe, not 128 equivalent probes. The maximum legal plan therefore requires
at most 976 seconds and fits the 1200-second preflight ceiling.

An omitted preflight setting derives `max(10, requiredProbeSeconds)`. An
explicit value below `requiredProbeSeconds` is a config-validation error at
the preflight JSON path and reports the required minimum; doctor reports both
the derived requirement and effective budget. Individual status-hook runs are
still clipped to the smaller of their configured timeout and the remaining
total preflight/status/recovery budget. Cancellation, execution failure, or an
unexpected scheduling overrun can therefore leave a probe unknown, but a
valid static configuration is never incapable of completing solely because
its declared hook timeouts exceed the declared preflight. Unprobed profiles
are explicitly `unknown`, never assumed stopped.

Except for the explicitly non-interruptible workload/action commit safety
cases, the operation hard deadline is exact: MCP start is preflight plus one
shared process-start budget plus attachment plus one reconciliation second;
connect is its attachment budget plus one reconciliation second; stop/kill is
its optional embedded recovery budget plus action and verification allocations
plus one reconciliation second—exact selected-snapshot budgets when identity
is already trusted, otherwise the independently pinned maximum-candidate
budgets described above; recover is its requested total budget plus one
reconciliation second. Lock acquisition is before acceptance and is not added
to the internal deadline. For built-in fallback actions, stop uses 30 seconds
and kill uses 10 seconds unless a future version adds an explicit bounded
setting.

That start formula describes MCP start. CLI start deliberately defers
attachment, so its normal hard deadline is preflight plus the one shared
process-start budget plus one reconciliation second and its successful
terminal outcome is `started_attachment_deferred`.

The normal MCP `games_start` handler spends at most the smaller of 20 seconds
and the effective preflight budget waiting in preflight. If the plan is still
running and its internal `phaseDeadline` is still in the future, it returns
`preflight_pending`, `processCreated: false` (at response time),
`processCreationPending: true`, the operation ID, and its background deadline;
the accepted operation continues and may spawn after preflight succeeds. If
preflight completes inside that response slice, the handler may additionally
wait through process-start verification and the smaller of 20 seconds and the
remaining attachment budget.

Every `games_start` response-slice expiry uses the same deterministic tie rule
as connect and recover: reacquire the per-game lock, prefer a terminal record
already committed, and return a pending result only when the current phase is
non-terminal and `now < phaseDeadline`. At a coincident response/phase
deadline, the handler uses the fixed reconciliation grace to commit/read the
phase's terminal matrix result; expired preflight can no longer authorize a
spawn, and expired attachment is not reported as `waiting`. The sole exception
is the separately documented non-interruptible spawn commit, whose pending
state deliberately survives its nominal deadline while retaining the lock and
occupancy.

The maximum normal response bound is advisory-lock acquisition (at most 5
seconds) plus the preflight response slice plus process-start verification
plus the attachment response slice and, only at a coincident phase deadline,
at most one reconciliation second. Later slices are included only when their
phases are reached. The full operation continues under its exact hard
deadline. CLI start has no resident manager after it exits, so it waits through
the full bounded preflight and process-start phases before returning its normal
attachment-deferred result. If a workload spawn is already non-interruptibly in
flight at that deadline, the CLI must remain resident until PID/failure is
durably published; it cannot return `started_attachment_deferred` or abandon
the commit. It then returns `spawn_commit_resolved_after_deadline` with the
reconciled occupied/failed state. This explicit commit-safety wait may exceed
the nominal CLI hard deadline; forced CLI termination leaves durable
`spawnState: prepared` for the ambiguity-safe recovery path.

A connect caller's absolute deadline is handler-entry plus its requested
timeout, while a newly accepted internal attachment receives that numeric
duration from acceptance. Time spent acquiring the lock can therefore make
the caller return `attachment_pending` before the internal attempt ends, but
can never make the caller exceed its requested bound.

Stop/kill caller wait begins at handler entry. Expiry before durable acceptance
has no lifecycle side effect; expiry afterward returns the documented pending
result when the response channel is available, but one final locked read makes
a terminal record already committed at that instant win over
`termination_pending`. For connect, if caller and attachment deadlines
coincide, the handler performs the same locked read: it returns a terminal
record already committed at that point, otherwise `attachment_pending`; the
internal publisher has only the fixed one-second reconciliation grace. This
removes timer-order ambiguity without extending the caller's requested bound.

Cancellation before an operation is accepted has no side effect. Cancellation
after the persisted transition detaches only that caller's wait and carries no
response-delivery guarantee. The operation continues under its internal
context and remains visible by operation ID until terminal; unresolved
liveness moves the runtime claim to `occupied_unverified`. MCP callers never
remain open for an internal continuation. Hook waits, bridge waits, status
fan-out, and verification polling are always deadline-bounded. Only a
standalone CLI already inside the explicitly non-interruptible workload/action
commit may outlive its nominal bound until durable side-effect publication.

The finite maxima on previously unbounded `games_start.timeout` and
`games_connect.timeout` are an intentional v3 validation tightening, not
bit-for-bit API compatibility. Release notes call it out; formerly accepted
larger values receive `timeout_out_of_range` with the supported maximum and no
side effect.

The configuration maxima in the table apply when validating schema 1.1.
Version-1.0 top-level startup timeout values keep their historical
defaulting/positive, non-overflowing interpretation, including values above the
new 1.1 maxima; doctor warns but does not clamp them. An omitted MCP start
timeout continues to use that legacy configured value. Thus only an explicitly
supplied oversized public start/connect argument tightens existing v1.0
behavior.

Start is not successful until its recovery snapshot exists. Persist the
`starting` runtime phase before launching. If the final `active` update fails,
GABS retains occupied in-memory state and attempts a safe rollback; it never
authorizes another start merely because persistence failed.

Before bridge attachment, start terminal/progression rules are:

| Spawn/process evidence | Operation | Runtime | Outcome |
| --- | --- | --- | --- |
| spawn primitive reports failure | `failed` | no claim after absence is verified | `spawn_failed` |
| workload running before process-verification deadline | continue to `attachment` | `active` | `workload_started` |
| workload definitively stopped | `failed` | no claim after launcher tree is reaped | `workload_stopped_during_start` |
| workload unknown at phase deadline | `timed_out` | `occupied_unverified` | `startup_unverified` |
| workload conflicted after settling | `failed` | `occupied_unverified` | `startup_evidence_conflicted` |
| spawn primitive still in non-interruptible commit at caller budget | non-terminal `executing` | `starting` | `spawn_commit_pending` |

The last row remains under the spawn safety exception until PID/failure is
durable; caller expiry does not terminalize it.

Stop/kill results keep the facts separate: `operationAccepted` means the
request was durably persisted; nullable `actionStarted` reports whether the
external action is known to have begun; nullable `actionSucceeded` reports
whether a completed result met its configured success contract;
`actionInvocationState` exposes invocation progress/ambiguity; and
`terminationVerified` means the liveness/evidence policy proved stopped. No
single "command accepted" boolean conflates them. GABS verifies with the status
hook, strong process evidence, or the configured command-exit completion
policy:

- verified stopped with action-process hazard clear: close bridge state and
  remove runtime/controller state;
- still running: return runtime phase to `active` and report action outcome but
  still running;
- unknown/conflicted: report `stop_requested_unverified` or
  `kill_requested_unverified`, move to `occupied_unverified`, and preserve the
  active-launch snapshot.

Terminal operation state follows the goal (verified termination) while keeping
the action facts:

| Action result | Final workload evidence | Operation state | Runtime | Outcome |
| --- | --- | --- | --- | --- |
| any, action hazard clear | stopped/termination verified | `completed` | no claim | `terminated`; use `terminated_after_action_failure` or `termination_observed_without_action` when applicable |
| any, action hazard live/unknown | any workload evidence | `timed_out` | `occupied_unverified` | `action_process_unresolved`; report `terminationVerified` independently when workload is stopped |
| succeeded | running at verification deadline | `timed_out` | `active` | `action_succeeded_workload_running` |
| failed/not started | running | `failed` | `active` | `action_failed_workload_running` |
| action timed out | running | `timed_out` | `active` | `action_timed_out_workload_running` |
| succeeded | unknown/conflicted | `timed_out` | `occupied_unverified` | `stop_requested_unverified` / `kill_requested_unverified` |
| failed/not started | unknown/conflicted | `failed` | `occupied_unverified` | `action_failed_liveness_unverified` |
| action timed out | unknown/conflicted | `timed_out` | `occupied_unverified` | `action_timed_out_liveness_unverified` |

Caller wait expiry alone never terminalizes the operation. Default
`commandExit` evidence may make the first row apply after its verification
window; stronger contradictory evidence selects another row.

If an executor is lost with invocation state `prepared`, reconciliation first
records `may_have_started` and never replays the action. For an external hook,
it first seeks positive action-tree absence/reap evidence. Only if that clears
the hazard may fresh stopped evidence complete as
`terminated_after_ambiguous_action`, or fresh running/unknown/conflicted
evidence terminalize `cancelled` with
`executor_lost_action_may_have_started` and the corresponding active/
`occupied_unverified` claim. Without that proof, the hazard row applies
regardless of workload evidence. For a built-in PID/signal action, the hazard
is structurally clear because no child was created; the same fresh workload
evidence reconciles the nullable action facts directly, still without replay.
The action-kind distinction and redacted evidence remain in terminal history.

The unresolved-action hazard overrides that ordinary evidence mapping. A
non-interruptible action commit that resolves after its action/hard deadline
has three explicit paths:

- definitive invocation failure publishes `failed`, `actionStarted: false`,
  `actionSucceeded: null`, and hazard `clear`, then terminalizes `timed_out`
  with `action_commit_failed_after_deadline`, `terminationVerified: false`,
  and the pre-action active/occupied claim; and
- a late-started external hook publishes `started`, `actionStarted: true`,
  `actionSucceeded: null`, and hazard `live`. No expired action or verification
  budget is restarted and no status hook, cancellation, wait, or reap runs
  after the commit overrun. The operation immediately terminalizes
  `timed_out`/`action_process_unresolved`, retains
  `runtimePhase: occupied_unverified`, and leaves the tracked action hazard for
  explicit recovery; and
- a late-completed built-in PID/signal action publishes `finished`,
  `actionStarted: true`, `actionSucceeded: true`, and hazard `clear`. It
  likewise runs no post-deadline liveness check. The operation immediately
  terminalizes `timed_out`/`builtin_action_completed_termination_unverified`,
  retains `runtimePhase: occupied_unverified` and the active-launch snapshot,
  sets `terminationVerified: false`, and directs the caller to explicit
  recovery before considering another action.

The standalone CLI returns that terminal late-commit result after durable
publication and terminal-record persistence; it never leaves an unrecorded
continuation. When an external hook has a live/unknown action child, its
persisted hazard blocks every new workload/action until a later
`games_recover` obtains positive reap/absence evidence or the user explicitly
force-forgets it.

Post-stop/kill verification polls until a distinct verification deadline so a
GABP disconnect, process exit, and external status can converge. Only the final
contradictory observation is `conflicted`; GABS never deletes its GABP client
connection/controller early merely to manufacture agreement.

A failed, timed-out, or interrupted hook may have partially succeeded. GABS
therefore always reconciles fresh evidence rather than blindly restoring or
replaying the previous state: verified stopped cleans up only when the
action-process hazard is clear, verified running returns runtime phase to
`active` with the terminal operation failure, and unknown/conflicted becomes
`occupied_unverified`. Recovery from a persisted
`stopping`/`killing` runtime phase verifies first and never automatically
replays a possibly non-idempotent hook. Controller, bridge, runtime snapshot,
and active profile survive until termination is verified. Cleanup is never
deferred unconditionally before a fallible lifecycle action. Removing active
runtime/controller state never removes the independently retained terminal
operation record.

### Bridge attachment semantics

Bridge attachment is a lifecycle operation, not an implicit reason to launch
again. The following rules retain the current meaning of
`games_start.timeout` while applying the explicitly documented v3 bounds:

For this contract, attachment includes endpoint acquisition, GABP handshake,
and successful initial tool synchronization. `connected` therefore means the
bridge is usable through GABS, not merely that a socket opened.

- `games_start.timeout` is an integer number of seconds in the inclusive range
  1..3600. When omitted, it uses the snapshotted
  `timeouts.startup.gabpConnectSeconds` value, whose default remains 60
  seconds. It pins the total internal attachment budget for that start
  generation. The separate process/status start deadline remains
  `timeouts.startup.processStartSeconds`, whose default remains 10 seconds.
  The MCP call waits for at most the documented initial response slice (20
  seconds, or the remaining smaller attachment budget). It returns bridge
  state `waiting` only while the attachment phase deadline is still in the
  future; a coincident deadline uses the terminal-record-first tie rule and
  returns the terminal attachment matrix result.
- `games_connect.timeout` is an integer number of seconds in the inclusive
  range 1..600 and defaults to 15 seconds. If no attachment operation is
  active, it starts one whose internal attachment deadline and normal caller
  wait use that value.
- If a start/connect attachment operation is already `waiting`,
  `games_connect` joins it instead of creating a parallel attempt. Its supplied
  timeout bounds only that joining caller's wait and never extends, shortens,
  or replaces the already pinned internal deadline. Caller wait expiry returns
  the non-error outcome `attachment_pending` when a response channel remains
  available.
- Transport cancellation before acceptance has no side effect. Cancellation
  after acceptance only detaches that caller; the accepted operation continues
  to its internal deadline and remains observable by operation ID. There is no
  response-delivery guarantee to a cancelled transport.
- `idle` means a bridge is expected, but no connection/attempt is active and
  attachment may be tried. CLI start ends in `idle` with
  `started_attachment_deferred`; a restart maps a never-attached launch to
  `idle`. `waiting` means exactly one current-generation attachment attempt is
  active. `connected` means that generation has a usable GABP connection and
  initial tool sync. `disconnected` means it connected previously and the
  connection closed, including after restart when an in-memory connection
  cannot survive. `unavailable` means no connection or attempt is active and
  either the internal deadline expired or current diagnostics prove attachment
  is not presently possible. `not_expected` applies only when no current
  workload/operation expects a bridge. Results always include `retryable` and
  the evidence supporting the classification.
- Attachment terminalization follows one matrix:

  | Final evidence | Operation | Runtime | Bridge | Outcome |
  | --- | --- | --- | --- | --- |
  | usable GABP + initial sync | `completed` | `active` | `connected` | `attachment_connected` |
  | deadline + workload running | `timed_out` | `active` | `unavailable` | start `started_bridge_unavailable`; connect `attachment_unavailable` |
  | deadline + workload stopped | `failed` | no claim | `not_expected` | start `workload_stopped_before_attachment`; connect `no_running_workload` |
  | deadline + workload unknown/conflicted | `timed_out` | `occupied_unverified` | `unavailable` | `attachment_liveness_unverified` |
  | manager supersession | `cancelled` | decided by superseding operation | `idle` if never connected, otherwise `disconnected`; becomes `not_expected` only after verified termination | `superseded_by_stop` / `superseded_by_kill` |
  | executor lost | `cancelled` | reconciled from workload evidence | stopped/no claim -> `not_expected`; running/occupied -> `idle` if never connected, otherwise `disconnected`; unknown/conflicted uses the same prior-connection rule with `occupied_unverified` | `executor_lost` |

  An attachment operation has no live attempt after a terminal row.
- A later `games_connect` may move retryable `disconnected`/`unavailable` state
  to `waiting` under a new operation generation. It never relaunches the
  workload, changes the active profile, or reapplies launch inputs. An already
  connected call remains process-idempotent and preserves current behavior by
  performing a bounded tool re-sync, explicitly reported as `resynced`,
  without creating a new attachment operation.

When no trustworthy runtime snapshot exists, `games_connect` does not silently
create a managed attachment operation. It may perform a foreground,
non-persisted observational attach only when endpoint/ownership evidence makes
that safe; cancellation ends that attempt and no background work is promised.
The result explicitly has `attachmentMode: observational`, no operation ID,
`runtimeClaimPresent: false`, and either a usable live bridge or a terminal
bounded observation—never `attachment_pending`. Start remains blocked by live
GABP/workload evidence. Managed results use `attachmentMode: managed`.
Background attachment requires first reconstructing a snapshot through
`games_recover`; stop/kill likewise require the trusted recovery rules below.

These distinctions also prevent an agent from interpreting a slow bridge as a
failed process launch or from issuing a duplicate start while attachment is
still legitimately pending.

## Runtime state and security

`runtime.json` becomes a versioned operational snapshot, not a copy of current
configuration.

It stores the minimum state required for safe recovery:

- runtime schema version;
- canonical game ID and display metadata;
- `snapshotKind: active|recovered|occupancy_only`; trusted active/recovered
  snapshots have authoritative `profileState: unprofiled|selected` and, for
  the latter, `selectedProfile`, while occupancy-only may have a separate
  evidence-labeled `observedActiveProfile` with provenance/observation time
  but no termination authority;
- separately labeled attempted profile/revision/input names for start
  diagnostics, never active attribution;
- config content revision;
- `appliedLaunchInputsState: known|unavailable`; an active snapshot created by
  GABS stores the sorted applied names with `known`, never values, while a
  snapshot reconstructed solely from external evidence uses `unavailable`
  and omits the names because that evidence cannot recover them. Names cannot
  reconstruct an identity-affecting value, so the config contract forbids
  inputs from carrying lifecycle identity;
- launch mode and process identity/fingerprint;
- runtime phase/generation and owner/lease metadata;
- start `spawnState` (`preflight|prepared|spawned|failed`) and durable PID
  fingerprint when available;
- stop/kill `actionInvocationState`
  (`not_started|prepared|started|finished|failed|may_have_started`), nullable
  action-start/success facts, and durable action PID/target fingerprint when
  available;
- `actionProcessHazard: clear|live|presence_unknown` plus the positive
  absence/reap evidence required before clearing it;
- last-known bridge state, whether this generation ever connected, and its
  observation time, used only for restart downgrade/diagnostics;
- the current non-terminal operation ID, kind, state, outcome-so-far,
  executor instance ID/PID fingerprint, accepted/start times,
  `operationPhase`, pinned phase-budget values, and absolute `phaseDeadline`
  and `hardDeadline`, including the single shared `processStartDeadline` for a
  start's spawn/verification phases;
- pinned status/stop/kill recovery specs required for recovery; and
- enough display metadata to keep an active entry diagnosable after its config
  definition is removed.

`runtime.json` remains GABS-owned lifecycle/ownership state. It is not a live
bridge-connection source for the game-side bridge or for agent recovery.

Each canonical game directory also has an independent owner-only
`operations.json` journal. The current non-terminal operation lives inside
`runtime.json` so acceptance/runtime phase/generation commit in one atomic
replace. The journal retains the newest 32 terminal records in deterministic
newest-first order. A terminal record contains only operation ID, generation,
kind, state, stable outcome code, accepted/started/finished timestamps, final
phase/hard deadlines, separately labeled selected/observed/attempted profile
attribution as applicable, applied input names, final action invocation/start/
success/hazard facts, final runtime/workload/bridge snapshots with observation
time, and redacted evidence summaries. It never contains launch-input values,
resolved argv/env, hook output, tokens, or a host-environment snapshot. Writes
use the same `0600`, flush, and atomic-replace discipline as runtime state.

The journal survives successful removal of `runtime.json` and GABS restart, so
an accepted operation can still be queried by ID after verified termination.
Pruning is count-based rather than wall-clock dependent. `games_status` returns
the current and most recent operation by default; with `gameId` and
`operationId`, it returns the matching current/retained record or
`operation_not_found`. Runtime cleanup never removes the journal, while an
explicit `--forget-runtime` removes only the runtime claim and also leaves the
journal intact. No MCP operation deletes retained operation history.

Terminalization uses a write-ahead, operation-ID-idempotent protocol because
two files cannot be atomically replaced together:

1. under the advisory lock, upsert the terminal record into
   `operations.json`, flush, and atomically replace it;
2. then update or remove `runtime.json` only if its current operation ID and
   generation still match; and
3. treat a repeated terminal upsert of the same ID and identical content as a
   no-op, while conflicting content is corruption.

Startup/status/recovery repairs every crash window without replaying external
actions. A terminal journal record plus matching non-terminal runtime record
finishes only the runtime reconciliation. A non-terminal runtime record whose
executor fingerprint is dead is orphaned. Recovery uses its persisted phase.
Because `spawnState: preflight` is durably published before locks are released
and means process creation was never attempted, an orphaned preflight is
terminalized `cancelled`/`executor_lost_during_preflight`; its attempted claim
is removed, and any following status/recovery/start performs fresh bounded
liveness reconciliation from the current immutable config. It does not resume
or trust partial old probe results.

`prepared` never spawns again and follows spawn-ambiguity recovery; `spawned`
resumes only remaining process/liveness verification; and `attachment`
resumes only its remaining budget. For `prepared`, definitive running evidence
recovers the launch, but ordinary workload-stopped evidence does not prove
that spawn had no side effect. Only positive spawn-side-effect absence proof
terminalizes `executor_lost_before_spawn`; stopped without that proof and
unknown/conflicted remain `occupied_unverified`. Other start evidence follows
the normal start/attachment matrix. An orphaned connect can resume only its
attachment phase. An orphaned stop/kill `recovery` phase terminalizes
`cancelled`/`executor_lost_during_recovery`, preserves occupancy, and reports a
fresh-recovery next action; no lifecycle action was authorized. In `action`, a
persisted `prepared` invocation becomes `may_have_started`; `started` may
monitor its fingerprinted child only for the remaining pinned action budget;
neither state ever invokes the action again. Both reconcile through fresh
liveness and the ambiguous-action matrix above. An orphaned `verification`
resumes only its remaining evidence budget. Recover may resume only bounded
observational evidence collection and idempotent reconciliation. No orphan
path invokes workload creation or a new lifecycle action. A runtime record
without a terminal journal entry remains the accepted source of truth; a
terminal journal entry without runtime is already complete. Mismatched
generations/IDs that cannot be explained by these rules become
`runtime_state_corrupt` and remain occupied. Crash-injection tests cover every
point before, between, and after both atomic replacements.

For every hook, the recovery spec stores the absolute command, absolute
selected working directory, resolved args, the fully resolved config-controlled
unset/env layer (including inherited game/profile values when requested),
`timeoutSeconds`, status running/stopped exit-code sets or stop/kill success
codes, post-action verification budget, and stop/kill `completionEvidence`.
It also snapshots built-in fallback semantics required when a hook is absent,
including `stopProcessName`, fingerprinted PID identity, and the applicable
graceful/force policy. Recovery never borrows changed defaults from current
config.

The spec never snapshots the inherited host environment. After restart, GABS
reconstructs a fresh sanitized OS base and reapplies the pinned explicit
values. This intentionally keeps unrelated inherited credentials out of
runtime state while preventing config reload from changing the selected hook.

Those explicit values may still be sensitive. Therefore:

- runtime directories are owner-only (`0700`) where supported;
- runtime files are owner-only (`0600`);
- writes use a unique same-directory temporary file, flush/close, and atomic
  rename;
- readers never observe partially written JSON;
- hook args/env are redacted from MCP results and normal logs;
- launch-input values and the launched process's full environment are never
  persisted; and
- old runtime schemas remain readable with explicit degraded diagnostics.

CLI config writes use the same atomic-write discipline and create files as
`0600`, because version-1.1 config can contain environment values. GABS does
not silently chmod a manually managed config, but doctor/status warns when a
sensitive config or runtime file is broadly readable.

An active game removed from config remains visible and addressable by its
canonical runtime ID with `configured: false`. Status-all includes active
unconfigured runtime entries. Stop/kill use the launch snapshot, never a newly
reused or renamed config entry.

If a new config definition reuses an ID while an older active snapshot exists,
the active snapshot continues to own connect/status/stop/kill routing and new
starts are blocked. Discovery reports both `activeDefinitionRevision` and
`configuredDefinitionRevision` until the old launch is verified stopped; GABS
never silently attaches the active runtime to the new definition.

A missing-field legacy snapshot may be recoverable, but syntactically corrupt
or internally inconsistent runtime/lock state is `unknown` and occupied until
the recovery service proves it stale or the user deliberately forgets it.
Agents and users are not directed to inspect or delete internal files by hand.

## Automatic config reload

Replace captured startup `*GamesConfig` pointers with a concurrency-safe
`ConfigStore`. Every config-dependent operation asks the store for an immutable
snapshot.

The store:

- content-hashes the config file and parses only changed hashes;
- caches an invalid hash so it is not reparsed on every call;
- deep-copies and publishes a valid snapshot atomically;
- retains the last valid snapshot plus the newest invalid revision/error;
- validates the whole document, not only entries added through the CLI;
- returns JSON-pointer-style field locations such as
  `/games/adventure/profiles/combat-test/args/1` rather than promising source
  line/column positions the current decoder does not track; and
- makes list/diff output deterministic.

If initial config is absent, the existing empty-config behavior remains. If a
previously valid config disappears or becomes invalid, it is not treated as an
intentional empty configuration.

If a config file exists but is invalid on initial server startup, normal MCP
and HTTP server startup fails with the validation error; there is no last-known
good snapshot yet. In particular, HTTP must not fall back to an empty/default
configuration and accidentally weaken a configured API-key policy. The
out-of-process CLI doctor/config-edit path remains available to diagnose and
correct the file.

### Last-known-good behavior

When disk config is invalid:

- new starts are blocked, preventing launches from stale definitions;
- read-only discovery/status uses the last valid snapshot and clearly reports
  `configStale`, invalid revision, and validation error;
- connect/stop/kill for active launches continue from runtime snapshots; and
- correcting the file automatically clears the error on the next operation.

### Hot and startup-only fields

Hot-reloaded fields:

- `games`, including profiles, launch inputs, and lifecycle hooks;
- `portRanges` for future endpoint allocation;
- startup/session timeouts for future operations.

Startup-only fields:

- `apiKey`, because authentication is already established; and
- `toolNormalization`, because public tool registration/names are already
  established; and
- `stripOutputSchema`, because it changes the cached `tools/list`
  representation and GABS does not currently advertise list-changed events.

`games_reload_config` invokes the same load path and returns:

- whether content changed;
- old and new revisions;
- added, updated, and removed canonical IDs;
- active IDs removed from config;
- warnings and validation errors;
- last-known-good status; and
- startup-only changes requiring process restart.

Automatic reload means users do not need to call this tool. It exists because
explicit verification is valuable to agents, scripts, support, and invalid
config recovery.

Each start pins exactly one immutable snapshot and revision before validation.
A reload during startup affects only future starts.

## MCP surface

V3 adds a small fixed set of core tools, but the set remains static during a
server session and never changes per game, profile, input, or bridge. Profile
metadata does not create dynamic tools or `tools/list` churn.

Every new or changed core-tool schema sets root `additionalProperties: false`,
and every handler independently rejects arguments outside that schema. This
applies to start, status, connect, stop, kill, doctor, recover, reload, show,
and list—not only to the profile-bearing call that exposed the original typo.

### `games_start`

Add:

- `profile?: string`; and
- `launchInputs?: object` whose values are boolean, string, or integer.

Keep existing `gameId`, `timeout`, and `resetEndpoint` meanings, subject to the
documented strict argument validation and finite timeout maximum.

The static MCP schema cannot enumerate hot-reloaded input names. It therefore
uses a generic primitive-value object, while the handler validates names,
types, constraints, and profile applicability against the pinned config
snapshot.

Set root `additionalProperties: false` and also reject unknown handler
arguments at runtime. Do not silently ignore `args`, `env`, `extraArgs`,
misspelled fields, or any future undeclared property merely because a client
failed to enforce the advertised schema.

Results include:

- canonical game ID;
- selected/active/requested profile as applicable;
- launch mode and a concise target summary suitable for distinguishing
  configured identities without exposing launch environment;
- config revision;
- `appliedLaunchInputsState` and, only when `known`, names of applied launch
  inputs; never their values;
- operation ID/state, workload state, bridge state, and ownership state;
- whether a pending transition is retryable, its suggested retry delay, and
  the bounded background deadline whenever preflight, spawn commit, process
  verification, or attachment continues asynchronously;
  and
- structured next actions.

Starting profile B while profile A is active never starts a second instance.
It reports both profiles and the evidence keeping A occupied.

A repeated start while the game is already `starting` or `running` is
idempotent with respect to process creation: it returns the current persisted
operation/runtime, sets `processCreated: false`, and never spawns another
process. Every repeated response also sets `requestedContextApplied: false`;
the comparison describes the already-active launch and never claims this call
applied anything. The exact comparison is:

1. resolve the request without side effects and normalize to effective applied
   input names (`boolean: false` is omission);
2. active profile unknown -> `unknown_active_profile`;
3. active/requested definition revisions differ ->
   `unknown_definition_revision`;
4. known profile differs -> `mismatched`;
5. active applied-input state is unavailable -> `unknown_active_inputs`;
6. known effective input-name set differs -> `mismatched`;
7. same profile/revision with an empty effective input set -> `matched`; and
8. same non-empty set -> `unknown_value_comparison`, because values are
   intentionally neither persisted nor fingerprinted.

`requestedContextMatch` uses exactly those six outcome strings. The active
launch context remains authoritative, and launch-input values remain secret
and are not echoed.

For result fields, workload state and bridge state are independent. A useful
minimum vocabulary is
`not_started|starting|running|stopped|unknown|conflicted` for the workload and
`not_expected|idle|waiting|connected|disconnected|unavailable` for the
bridge. A workload-running/bridge-waiting result is not a failed launch and
never triggers an automatic relaunch or profile switch. When the bridge is
already connected, `nextActions` proceeds to discovery and never recommends a
redundant `games_connect`.

### `games_show`

Return:

- canonical game identity;
- launch mode plus the same concise target summary used by list/status/start;
- sorted profile names and descriptions;
- configured default profile;
- launch-input names, descriptions, JSON-Schema constraints, and profile
  applicability, plus the fixed `lifecycleIdentityUse: forbidden` contract;
- current config revision and reload health;
- launch-mode propagation capability; and
- relevant warnings/next actions.

Normal AI-facing discovery does not expose input argv/env templates or secret
environment values. A local diagnostic/config view may show redacted mapping
structure for debugging; hiding it is not presented as a security boundary.

### `games_doctor`

Add a stable MCP counterpart to the existing CLI doctor and make both
profile-aware for the common "why will this not start?" loop. With `gameId`
and optional `profile`, it checks:

- config version/revision health and full validation;
- profile/default/input references;
- launch-mode propagation capability;
- target, working-directory, and lifecycle-command resolvability;
- placeholder completeness and effective non-secret launch structure;
- an informational `launch_input_lifecycle_identity_contract` finding for each
  declared input, explaining that any value needed by status/stop/kill or
  restart recovery must become profile context;
- config/runtime file permission warnings;
- active runtime compatibility and profile identity; and
- optional status-hook observation when `probeStatus: true`.

Without a profile, it checks the legacy/default launch or every configured
profile as appropriate. It never starts, stops, kills, rewrites config, or
exposes configured secrets. Findings have stable codes, severity, field paths,
and exact next actions. This keeps troubleshooting inside GABS instead of
requiring users and agents to reverse-engineer process setup.

### `games_list`

Keep compact text output. Structured content adds launch mode, a concise target
summary, sorted profile names, default profile, and config health. The summary
contains `targetKind`, `targetLabel`, and `targetFingerprint`. For path-like
targets, the label is the basename when unique among same-mode entries; on a
collision it expands to the shortest trailing path-component suffix that is
unique, prefixed with an ellipsis. For opaque targets it is the configured
opaque identifier. The fingerprint is `sha256:` plus the first 12 lowercase
hex digits of the normalized effective target; it is a stable discriminator,
not a security boundary. Exact duplicates intentionally share it. The summary
never contains argv, environment, tokens, or hook commands. This distinguishes
same-basename installations without turning list into a full config dump.
List/show/status/start use the same helper and deterministic ordering.

### `games_status` and `games_connect`

Both may accept `profile?: string` strictly as a recovery/query hint when no
trusted active-profile snapshot exists. A supplied name alone is never treated
as evidence. It only prioritizes the hinted profile's observation; trusted
attribution still runs every applicable exclusion probe and requires every
competing profile to be definitively excluded. Results state whether the full
evidence set confirmed the hint.

`games_status` may also accept `operationId?: string` when `gameId` is
provided. This selects the matching current runtime operation or retained
terminal-journal record without changing runtime state. `games_connect`
follows the join/retry/deadline rules in
"Bridge attachment semantics"; in particular, it never creates a second
attachment attempt for a generation that is already `waiting`. It retains
existing `forceTakeover?: boolean` behavior, but takeover is explicit,
recorded, and cannot select or change a profile.

An operation-ID query returns two labeled envelopes. `queriedOperation` is
either a point-in-time snapshot of the mutable current runtime operation
(`terminal: false`, with no finish snapshot) or an immutable terminal-journal
record (`terminal: true`, with evidence/final-state snapshots at finish).
`current` is separately timestamped current status from the normal bounded
observation path. Historical fields are never silently filled from current
state; if an old degraded terminal record lacks a final snapshot, that field is
explicitly unavailable.

Report:

- active profile when known;
- `running`/`stopped`/`unknown`/`conflicted`;
- separate runtime, operation, workload, bridge, and ownership domains, each
  with its source/observation time, plus operation ID, retryability, retry
  delay, and deadline when a transition is pending;
- launch mode and concise target summary for the selected game identity;
- summarized evidence and the status source;
- `actionProcessHazard`, `releaseSafe`, its last positive/unknown process-tree
  evidence, and the only permitted clearing path (`games_recover` positive
  reap/absence or explicit local force-forget);
- configured/unconfigured state;
- config revision health; and
- precise `nextActions`.

No agent-facing recovery instruction uses `runtime.json` or
`GABS_BRIDGE_PATH` as live bridge truth.

### `games_stop` and `games_kill`

Use the persisted active-launch snapshot. Callers normally do not repeat a
profile. Return `operationAccepted`, nullable `actionStarted`, nullable
`actionSucceeded`, `actionInvocationState`, `actionProcessHazard`,
`terminationVerified`, and `releaseSafe` as separate facts. A non-clear hazard
always sets `releaseSafe: false` and returns its recovery/force-forget next
action even when workload termination was independently verified. Add:

- `profile?: string`, accepted only as a recovery hint when no trustworthy
  snapshot exists and `trustedActiveProfileEvidence` confirms that profile;
- `timeout?: number`, an integer caller-wait budget in seconds from 1 through
  600 inclusive, defaulting to 20 seconds. It bounds this caller's total wait
  from handler entry, including lock acquisition, recovery, action, and
  verification. It is not permission to change the snapshotted hook timeout,
  verification budget, operation phase/hard deadlines, or escalation policy;
  and
- `forceTakeover?: boolean`, required to override another active runtime-owner
  lease.

Neither field by itself authorizes a lifecycle hook against an uncertain
target. When no snapshot exists, stop/kill remains one accepted, observable
operation by entering its persisted `recovery` phase, using the exact same
evidence rules as `games_recover`, and then executing only an atomically
promoted recovered snapshot. It never runs an ephemeral stop/kill hook directly
from current config. If reconstruction cannot establish trusted active
profile/unprofiled identity, the operation terminalizes with
`recovery_required` or `recovery_timed_out` without acting.

Once a termination operation is accepted, client cancellation or expiry of
the caller wait budget does not erase or replay it. An accepted operation whose
explicit wait budget expires returns, while its response channel remains
available, a
non-error tool result with `operationAccepted: true`, the current
`actionStarted`/`actionSucceeded` facts, `terminationVerified: false`,
`outcome: termination_pending`, runtime phase `stopping` or `killing`,
operation state `executing` or `verifying`, operation phase (including
`recovery` when applicable), operation ID, current evidence, phase/hard
deadlines, and exact status/recovery next actions. An unresolved invocation
commit instead reports `action_commit_pending` and nullable action facts.
Transport cancellation after acceptance has the same continuing operation
semantics but no response-delivery guarantee. The persisted manager continues
only until its own bounded recovery/action/verification deadline, except for
the explicitly documented non-interruptible commit safety case.
`games_status` exposes that same operation, and recovery verifies before
considering any replay because a stop hook need not be idempotent. Zero,
negative, fractional, string-valued, or over-limit timeouts are validation
errors with no lifecycle side effect.

### `games_recover`

Add a bounded recovery service so `unknown`, corrupt/orphaned coordination
state, or a stale owner lease cannot permanently brick a game ID or force
users to delete internal files.
With `gameId`, optional `profile`, and optional integral `timeout` (1..1200
seconds, default 20), the MCP form:

- collects all liveness, ownership, lock, workload/action-process, and profile
  evidence;
- repairs an unequivocally stale owner lease, runtime phase, journal record, or
  advisory-lock diagnostic metadata; it never "repairs" or deletes the OS
  advisory lock itself, whose handle release already provides crash recovery;
- upgrades a readable legacy snapshot;
- reconstructs a missing snapshot only when
  `trustedActiveLaunchEvidence` proves either one active profile or explicit
  unprofiled identity;
- clears an action-process hazard only after positive tree absence/reap
  evidence; and
- otherwise preserves occupancy and returns the exact unresolved evidence.

At timeout, a committed terminal recovery result wins one final locked read;
otherwise an accepted repair returns `recovery_pending` and may use only the
fixed reconciliation grace. A purely observational recovery that never
accepted a state transition simply returns its bounded partial evidence.

The MCP form never forcibly forgets uncertain state. Forced forgetting is an
explicit local CLI administrative action described below.

Status and connect are observational when the active snapshot is missing; they
may report trusted profile evidence but do not create or replace runtime state.
Snapshot reconstruction occurs only through the shared locked recovery
transition, called explicitly by `games_recover` or internally by stop/kill as
described above. It pins one current immutable config revision, records
`recoveredFromConfigRevision` and that the original launch revision/spec was
unavailable, sets `appliedLaunchInputsState: unavailable`, and adopts current
lifecycle hooks only when trusted evidence confirms the same still-configured
selected profile or explicit unprofiled identity. If the profile was removed,
unprofiled target identity is ambiguous, an action-process hazard remains, or
no safe current lifecycle action can be established, recovery remains
`unknown`/`recovery_required` rather than pretending to restore the original
hooks.

### `games_reload_config`

Add this as a stable core tool. It verifies and reports the automatic reload
state; it does not mutate the config.

### Structured errors

At minimum, use stable codes for:

- `unknown_argument`;
- `profiles_not_configured`;
- `ambiguous_game_reference`;
- `profile_required`;
- `profile_not_found`;
- `launch_input_not_declared`;
- `launch_input_invalid`;
- `launch_input_conflict`;
- `config_invalid`;
- `schema_upgrade_blocked`;
- `same_identity_profile_ineligible`;
- `timeout_out_of_range`;
- `lifecycle_unknown`;
- `recovery_required`;
- `recovered_identity_action_unsupported`;
- `runtime_state_corrupt`;
- `action_process_unresolved`;
- `operation_locked`;
- `operation_not_found`;
- `active_profile_unknown`; and
- `multiple_profiles_running`.

Each pre-acceptance validation, selection, ownership, or lock error contains
facts, sorted candidates where relevant, and concrete next actions. Such an
error does not launch, stop, kill, or rewrite config. Config reload and
migration-planning errors likewise never rewrite config.

After a lifecycle action is accepted, failure, internal timeout, cancellation,
or incomplete verification is an operation outcome rather than a safe-to-retry
validation error. When a response can be delivered, GABS returns a non-error
structured result containing `operationAccepted: true`, the operation ID,
possible partial side effects, reconciled evidence, terminal/pending state,
and exact next actions. Action and termination facts remain separate. Clients
must observe that operation instead of automatically replaying it.

`unknown_argument` and other validation failures also include the JSON path,
expected name/type or constraint, and sorted allowed names. GABS may suggest a
single obvious spelling correction in `nextActions`, but never applies fuzzy
correction to an operational request.

## CLI surface

Add lifecycle commands backed by the same manager as MCP:

```text
gabs games start <id> [--profile NAME] [--input NAME=VALUE]... [--process-timeout SECONDS] [--reset-endpoint]
gabs games status [<id>] [--profile NAME] [--operation-id ID]
gabs games stop <id> [--profile NAME] [--force-takeover]
gabs games kill <id> [--profile NAME] [--force-takeover]
gabs games doctor <id> [--profile NAME] [--probe-status]
gabs games recover <id> [--profile NAME] [--timeout SECONDS]
gabs games recover <id> --forget-runtime --force [--timeout SECONDS]
```

- Each action has its own flag set; top-level flag parsing must not consume or
  reject action-specific flags first.
- Repeated `--input` names are errors rather than last-value-wins surprises.
- Values are parsed according to the declared type and validated by the shared
  resolver.
- Start `--process-timeout` is deliberately named differently from the legacy
  MCP `games_start.timeout`: it is an integer number of seconds from 1 through
  600 that overrides `timeouts.startup.processStartSeconds` for CLI
  workload-spawn plus process/status verification; both phases share that one
  absolute deadline. The CLI has no resident background GABP client after it
  exits, so it must not claim an attachment operation remains `waiting` there.
- Standalone CLI stop/kill has no caller-only `--timeout`: without a resident
  manager it remains alive to the operation's finite pinned recovery/action/
  verification hard deadline and returns a terminal result. Interruption may
  orphan the accepted operation, which is then handled by the same persisted
  no-replay recovery rules and remains inspectable by operation ID.
- Recover `--timeout` is integral from 1 through 1200 and defaults to 20. For a
  standalone CLI it is the evidence budget; the process then remains for at
  most the fixed one-second reconciliation grace and returns a terminal result,
  never a managerless `recovery_pending` continuation.
- `--operation-id` requires a game ID and reads the bounded retained operation
  state/history without changing lifecycle state: current runtime operation
  first, then the terminal journal.
- CLI start prepares endpoint/runtime state and verifies liveness, then exits
  without keeping a redundant GABP client. It records bridge state `idle` and
  outcome `started_attachment_deferred`; a later long-lived GABS server process
  attaches when `games_connect` is invoked. This normal result is unavailable
  while a workload spawn commit remains unresolved.
- A standalone CLI never intentionally returns a non-terminal operation. When
  it owns a non-interruptible workload/action commit, it stays resident until
  the primitive publishes durable success/failure, prints the explicit safety
  overrun, and returns the reconciled late-commit result. Forced termination
  relies on the persisted prepared-state recovery rules; it never pretends the
  side effect was absent.
- CLI status/stop/kill work from persisted snapshots after the original GABS
  or launcher process exits.
- Extend the existing CLI doctor to render the same profile-aware findings as
  `games_doctor`.
- Normal CLI recover shares the safe MCP recovery logic. `--forget-runtime`
  requires `--force`, prints the strong/uncertain evidence being overridden,
  explicitly warns when a live/unknown action process may later affect a new
  workload,
  and first acquires the stable advisory `operation.lock`. If another process
  holds it, even `--force` refuses and reports the owner/action. While holding
  it, recovery advances the persisted generation, invalidates late callbacks,
  terminalizes any abandoned current runtime operation into the journal as
  `cancelled` with outcome `runtime_forcibly_forgotten`, then removes only the
  resolved canonical game's `runtime.json` and clears lock diagnostic metadata.
  It never unlinks or renames `operation.lock`, kills a process, deletes
  `operations.json`, or clears endpoint-cache/debug state. The stable lock file
  remains after release. Forced forgetting is offered only after normal
  recovery cannot resolve the state.

## Smart, simple mapping of existing config

The migration model has two levels: zero-migration compatibility and an
explicit read-only consolidation plan.

### 1. Zero-migration compatibility

An existing version-1.0 game entry already has a precise interpretation:

    effective legacy launch = current game-level launch context

With no profiles, it starts exactly as before. Nothing is renamed, wrapped, or
rewritten, and GABS adds no profile-adoption or schema-migration warning merely
because the entry remains version 1.0. Unrelated pre-existing legacy warnings
such as nonpreferred IDs or map-key/contained-ID mismatches remain visible.

If an entry adds profiles while retaining game-level `args`, `env`, or
`workingDir`, those values are intentionally common base context. For a
version-1.0 document, the smallest migration is to bump the top-level version,
add profile overlays, and leave genuinely common fields where they are. An
already-version-1.1 document adds only the overlays; it has no version bump.

Enabling profiles is not literally behavior-neutral: the old unprofiled choice
is replaced by explicit/default profile selection. For a version-1.0 source,
the converted launch changes from no state marker to
`GABS_PROFILE_STATE=selected` and adds `GABS_PROFILE`; every surviving
untouched unprofiled entry changes from no marker to
`GABS_PROFILE_STATE=unprofiled`. For an already-version-1.1 source, the
converted launch changes its marker from `unprofiled` to `selected` and adds
`GABS_PROFILE`, while untouched entries have no managed-environment change.
Compatibility means the old version-1.0 entry with no profiles remains launch-
semantically unchanged until the user adopts 1.1; it does not mean profiles
can be added without a declared selection/metadata transition.

### 2. Freeze the current launch as an initial profile

When existing launch context is profile-specific, the safe transformation is:

1. create a profile named `current` (or a user-chosen name);
2. move all mutable launch context into it: `args`, `env`, `unsetEnv`,
   `workingDir`, and profile-overridable lifecycle hooks;
3. keep identity/transport fields at game level: ID, name, description, target,
   launch mode, effective GABP mode, and process-stop identity;
4. set `defaultProfile` to the new profile for a behavior-preserving omitted-
   profile call; and
5. prove resolver equivalence modulo the exact source-version-sensitive
   managed delta: version 1.0 has state marker `absent -> selected`, while
   version 1.1 has `unprofiled -> selected`; both add
   `GABS_PROFILE=<name>`.

If the user deliberately wants every future start to name a profile, the
planner may omit the default only when it labels `games_start <id>` ->
`profile_required` as an intentional behavior change. It then proves
equivalence only for `games_start <id> --profile <name>`.

"Resolver-equivalent" has a narrow, machine-checkable meaning:

- same user-configured target and launch mode;
- same argv elements;
- same configured non-managed environment after merge;
- same working directory; and
- same lifecycle action after placeholder resolution.

The report separately lists managed changes such as `GABS_PROFILE_STATE` and
`GABS_PROFILE`. When a canonical ID changes, it also lists `GABS_GAME_ID`,
endpoint/runtime/ownership identity, mirrored tool namespace and scripted ID
references, the loss of independent per-ID concurrency, and every
`${gameId}`/`${id}` lifecycle expansion. Any unresolved or behavior-changing
lifecycle delta prevents an unqualified "equivalent" verdict.

Moving all context is conservative. GABS cannot infer which old arguments are
common and which select an isolated environment. After conversion, the user
may deliberately hoist genuinely common values back to game level.

### 3. Classify duplicates, profile candidates, and separate identities

The planner does not assume that every pair of similar old entries should
become profiles. It performs a three-way classification:

The first planner version groups only unprofiled entries, for which there is
one effective mutable launch context. `--all` labels any profiled entry
`already_profiled` and excludes it from grouping. A scoped plan rejects a
profiled canonical or source entry with a manual-review next action; importing
or comparing complete profile sets is a separate future feature, not an
implicit flattening rule. Game-level `launchInputs` are not profile overlays:
all entries selected for consolidation must have the same normalized
declaration set, or the planner returns `launch_input_consolidation_blocked`
with a manual-review action and emits no patch.

1. **Exact config duplicates modulo ID cutover:** immutable identity and
   complete effective mutable launch context and normalized game-level
   launch-input declarations match after normalizing only
   managed/canonical-ID-derived substitutions. Recommend one canonical entry
   and removal of the redundant source definition; do not manufacture two
   indistinguishable profiles. The verdict is
   `equivalent_except_for_id_cutover`, never unqualified
   `resolver_equivalent` while concrete IDs differ.
2. **Same identity, different launch context:** immutable identity is
   compatible while args, env, unset-env, working directory, or lifecycle
   behavior differs and launch-input declarations remain common. These are
   profile candidates only when the launch mode is propagation-capable.
   Otherwise classify
   `same_identity_profile_ineligible` and recommend retaining separate IDs or
   manually moving to a capable launch mode; never emit a profile patch.
3. **Different identities:** at least one field in the closed immutable set
   below differs. Keep separate game IDs.

The immutable comparison set for schema 1.1 is closed and contains exactly:

- effective target;
- launch mode;
- effective `gabpMode`; and
- `stopProcessName`, which remains game-level.

ID, name, and description do not participate in compatibility grouping. ID is
still a managed runtime/bridge identity whose cutover effects must be reported;
name and description are canonical display choices. No other current field is
silently promoted to identity by an implementation.

"Effective" uses the shared, pinned, mode-aware helper in "Path and target
normalization." Path-like targets therefore use the config-directory base and
the exact Windows-folded/non-Windows-exact comparison policy defined there;
opaque targets use their validated canonical strings; launch-mode and
`stopProcessName` values remain exact validated strings; and omitted
`gabpMode` canonicalizes to `local` before comparison. A target that cannot be
resolved is not grouped. In schema 1.1, effective `gabpMode` is the complete
configured transport-identity grouping key. Derived `GABS_GAME_ID`, endpoint,
tool namespace, runtime, and ownership identities are reported cutover effects,
not compatibility keys. Any future schema field that changes configured
transport identity must update this closed set as a schema change rather than
being inferred by the planner.

The complete mutable-context comparison includes effective `args`, `env`,
`unsetEnv`, `workingDir`, and structured lifecycle hooks after legacy defaults
and path resolution. For classification only, `${gameId}` and `${id}` in hook
templates normalize to one symbolic game-ID token; their actual per-source
expansions remain mandatory cutover deltas. Literal embedded IDs are not
normalized. These fields are movable profile context when they differ.
Name/description come from the chosen canonical entry.

`launchInputs` are a separate game-level common-capability precondition, not
immutable identity and not movable profile context. Their normalized sets must
match across the canonical entry and every source: same input names,
descriptions, types, constraints, applicability sets, and literal args/env
bindings. JSON map order and set-like applicability order do not matter; argv
element order does. If any source adds, removes, or changes a declaration, the
planner reports the exact declaration paths and
`launch_input_consolidation_blocked`. It never unions inputs, silently chooses
one source, or broadens an input to profiles whose former game ID did not
expose it. A same-ID single-entry initial-profile freeze simply retains that
entry's declarations at game level.

This symbolic comparison does not weaken the earlier resolver-equivalence
definition. Concrete placeholder expansions still differ across source IDs,
so the report shows both actions and requires the identity/single-instance
cutover acknowledgement. Only a same-ID initial-profile freeze can receive an
unqualified `resolver_equivalent` verdict.

Exact-duplicate deduplication is still an identity cutover, not a casual alias
delete. The plan reports changes to `GABS_GAME_ID`, endpoint/runtime/ownership
identity, mirrored game-tool namespace/discovery names, scripted references to
the removed ID, and `${gameId}`/`${id}` expansions for the removed source ID.
It also reports that formerly separate IDs could be launched concurrently,
whereas one canonical ID is intentionally single-instance across all profiles.
It uses the same stopped-state checks, revision binding, explicit
single-instance-cutover acknowledgement, single-edit cutover, and rollback
instructions as profile consolidation. The result is simply smaller: no schema
bump or profile object is required unless the canonical entry is independently
being converted. Keeping separate IDs is the correct result when independent
concurrency or stable old namespaces are requirements.

If immutable fields differ, the entries remain separate game IDs. GABS reports
the exact diff instead of guessing or suggesting profiles.

Near-identical legacy wrappers may have different target paths even though the
user intends them to become one profile-aware wrapper. The default planner
refuses to call that mechanically equivalent. An explicit canonical-target
normalization option may generate a plan, but it marks the target change
unproven, explains that wrapper internals cannot be compared by GABS, and
marks application blocked until the immediate stopped-state recheck passes;
doctor and per-profile acceptance tests then gate completion. The user—not a
heuristic—chooses the canonical launcher.

This explicit path also covers wrappers whose old target path was the only
thing selecting an isolated context. If `--target` makes a source otherwise
identical, a bare source remains an exact-deduplication candidate. But a source
paired with `--as-profile`, together with `--canonical-profile` and
`--accept-profile-name-contract`, deliberately creates a name-only profile:
its profile object may contain no mutable overlay because the distinct managed
`GABS_PROFILE` value is itself the newly declared input to the canonical
wrapper. The result is labeled `unproven_profile_name_contract`, never
`resolver_equivalent`. GABS cannot prove that the replacement wrapper consumes
that value or routes status/stop correctly, so the plan requires the normal
single-instance cutover acknowledgement, reports active/unknown cutover IDs as
an application blocker, and requires doctor plus sequential start/status/stop
acceptance for every profile before completion. Ordinary same-target exact
duplicates cannot use this exception and remain dedup-only.

For same-identity entries with meaningfully different mutable context:

- choose one canonical game ID;
- turn each entry's complete mutable launch context into a named profile;
- keep canonical display/identity fields and the proven-common launch-input
  declarations at game level;
- compare every old launch against its proposed profile using the narrow
  resolver-equivalence contract above; and
- generate one single-edit cutover plan that replaces the canonical entry and
  removes the imported source IDs together.

Every such plan reports the same concurrency, tool-namespace, ID-reference,
and managed-identity cutover effects as exact deduplication. It does not label
the cutover acceptable or emit a machine-applicable patch until the caller
passes `--accept-single-instance-cutover`.

The planner reports whether all `cutoverGameIds` are stopped, but that
observation is advisory: a non-writing process cannot hold every lifecycle
lock while a human edits the file. It may emit the revision-bound plan while
an ID is active or unknown, but sets
`applicationBlocked: ["cutover_ids_not_verified_stopped"]`; such a plan is
neither machine-applicable nor complete. Immediately before editing, recheck
the config hash and stopped status of every cutover ID; a successful recheck
clears that application gate. Immediately after reload, recheck the removed
IDs and the canonical ID before starting anything. If an old source starts
during the window, it remains visible as an active unconfigured runtime: stop
it by its old ID and do not start the canonical profile until termination is
verified.

Keeping source IDs beside the canonical entry creates independent runtime
locks and a duplicate-launch window, so coexistence is reported as unsafe—not
as a testing strategy. A pre-edit config backup plus the recorded source
revision provides rollback rather than keeping two live definitions. V3 does
not claim that a read-only planner can make this manual window race-free.

V3 does not add hidden aliases or automatic source deletion. Both create
long-lived identity complexity for a one-time migration and can conceal an
incorrect consolidation. They can be reconsidered later if real compatibility
data justifies them.

### Read-only mapping assistant

Provide one coherent, revision-bound invocation:

```text
gabs games profiles plan --all [--probe-status]
gabs games profiles plan <game-id> --canonical-profile <name> \
  [--require-explicit-profile] [--probe-status] \
  [--format human|json-patch] [--include-sensitive]
gabs games profiles plan <canonical-id> \
  --from-game <exact-duplicate-id> [--from-game <exact-duplicate-id>]... \
  [--target <canonical-target>] \
  --accept-single-instance-cutover [--probe-status] \
  [--format human|json-patch] [--include-sensitive]
gabs games profiles plan <canonical-id> \
  --canonical-profile <name> \
  --from-game <candidate-id> --as-profile <profile> \
  [--from-game <candidate-id> --as-profile <profile>]... \
  [--from-game <exact-duplicate-id>]... \
  [--target <canonical-target>] \
  [--accept-profile-name-contract] \
  [--require-explicit-profile] \
  --accept-single-instance-cutover [--probe-status] \
  [--format human|json-patch] [--include-sensitive]
```

Before classification, the planner token-scans the raw source JSON for
duplicate member names at every object level. Any duplicate returns
`ambiguous_source_json` with deterministic paths/occurrences and emits no
patch, even when legacy schema-1.0 runtime loading would still accept the file
under its compatibility policy. A content hash cannot make an RFC 6902 JSON
Pointer unambiguous when parsers may select different duplicate members. The
user must remove the duplicate, reload, and request a new revision-bound plan.
`--all` may inventory the document only as blocked; it never classifies the
ambiguous entries as safe opportunities.

`--all` is a redacted hierarchical inventory. It first partitions entries into
immutable-identity groups; different groups are separate identities. Within
each group it first partitions by normalized launch-input declaration set.
Different sets are `launch_input_consolidation_blocked`, not profile
candidates. Within a common-input partition it then partitions entries into
mutable-context equivalence classes; members of one class are exact
duplicates, while multiple classes are profile candidates only for a
propagation-capable launch mode and otherwise
`same_identity_profile_ineligible`. It recommends opportunities but emits no
patch, chooses no canonical ID, and invents no profile names.

In a scoped plan, bare `--from-game <id>` is accepted only for an exact
duplicate. A meaningful mutable-context difference returns a next action
requiring the adjacent pair `--from-game <id> --as-profile <profile>`.
`--as-profile` binds only to the immediately preceding `--from-game`; it cannot
appear alone or after another option. This is unambiguous even when a legacy ID
contains `=`. Conversely, assigning a profile name to an exact duplicate is
normally rejected rather than manufacturing a redundant profile. The only
exception is the explicit target-normalized name-only wrapper contract defined
below.
A mixed plan may combine bare duplicate sources with named profile candidates;
`--canonical-profile` is required only when wrapping the canonical launch into
a profile or importing a meaningful context variant. Each bare source must
match exactly one selected output context class: the canonical context or one
named imported profile class. The plan reports that association. Zero or
multiple matches are errors, so a duplicate of a named imported candidate is
removed with that candidate's class rather than ambiguously attached to the
canonical profile.

By default, `--canonical-profile <name>` also sets `defaultProfile` to that
name, preserving an omitted-profile start. `--require-explicit-profile` omits
the default and records `games_start <id>` becoming `profile_required` as an
intentional behavior change. The flag is valid only when a canonical profile
is created.

Scoped preflight rejects a missing game, repeated source ID, the canonical ID
as a source, a source assigned more than once, duplicate destination profile
names, the canonical profile name reused by an imported profile, any profile
name collision, source/canonical entries already containing profiles, and any
non-identical normalized launch-input declaration sets.
`--target` is accepted only when at least one selected source differs solely by
target after substituting that explicit target, and the value is valid for the
canonical launch mode; it never masks another immutable-field difference. A
bare source may become an exact duplicate only after this acknowledged target
substitution, which is the target-only deduplication path. A named source that
becomes context-identical after substitution is accepted only when
`--canonical-profile` and `--accept-profile-name-contract` are both present,
the source originally differed by target, normalized launch-input declarations
are common, and the canonical launch mode can propagate profile context. The
flag is invalid without `--target` and at least one such named source. That
path emits `unproven_profile_name_contract`, empty/name-only overlays where
appropriate, explicit wrapper/lifecycle uncertainty, and mandatory per-profile
doctor plus sequential start/status/stop checks. Every other named exact
duplicate is rejected. Profile-producing plans fail with
`same_identity_profile_ineligible` when the canonical launch mode cannot
propagate profile context.

The exact `cutoverGameIds`, `schemaAffectedGameIds`, machine-readable
`wholeDocumentEffects`, destination profile-name set, normalized target, and
cutover acknowledgements are bound to `baseRevision`.

The command never writes. It returns:

- expected source config revision/hash;
- exact-duplicate/profile-candidate/profile-ineligible/separate-identity or
  explicitly unproven name-only wrapper-contract classification;
- compatible or incompatible identity verdict;
- exact immutable-field differences;
- fields classified as identity, `commonAcrossSources` informational
  candidates, proven-common launch inputs, and movable context;
- intentional managed-identity and unproven target deltas;
- sorted `applicationBlocked` codes derived from the advisory cutover-state
  observation;
- before/after resolved argv, working-directory, and redacted-environment
  equivalence;
- the required schema-version change; and
- edit -> reload -> show -> start verification steps.

`commonAcrossSources` never causes automatic hoisting in planner v1. Each old
entry's complete mutable context is kept together in its emitted profile.
Users may hoist genuinely common values only in a later explicit edit followed
by a separate resolver-equivalence review.

Because the version is top-level, any plan that introduces profiles first
constructs the complete proposed document in memory and strict-validates every
entry as schema 1.1. Unrelated entries are never silently repaired. If a
version-1.0 -> 1.1 plan finds an untouched legacy entry that would make the
upgraded file invalid, the planner returns `schema_upgrade_blocked` with
deterministic JSON paths and emits no patch. In that actual version-bump case,
unprofiled untouched entries need not be wrapped, but their next launch gains
the managed `GABS_PROFILE_STATE=unprofiled` marker. The plan lists that whole-
document managed-environment effect under `wholeDocumentEffects`, with every
surviving entry whose future launch changes listed in
`schemaAffectedGameIds`, separately from the lifecycle-sensitive
`cutoverGameIds`; it is never hidden inside a claim of byte-for-byte
environment equivalence. For a plan whose source is already version 1.1,
untouched entries have no schema-driven launch change and both schema-effect
fields are empty.

Planning is non-mutating across every GABS state surface: it never writes
config, runtime claims, the operation journal, lock metadata, or endpoint-cache
metadata; never acquires a lifecycle operation lock; and never performs
lifecycle reconciliation. By default, stopped-state reporting uses only
persisted/read-only evidence and labels its freshness. `--probe-status`
explicitly permits configured observational status hooks to run under their
normal bounds, but their results are returned only to the planner and are not
persisted or used to clean/claim runtime state.

Default human stdout is a redacted verdict and edit checklist, with
explanations on stderr. `--format json-patch` emits a secret-safe,
revision-annotated envelope:

```json
{
  "schema": "gabs-config-patch/v1",
  "baseRevision": "sha256:...",
  "cutoverGameIds": ["adventure", "adventure-test"],
  "applicationBlocked": [],
  "schemaAffectedGameIds": ["adventure", "factory"],
  "wholeDocumentEffects": [
    {
      "code": "managed_profile_state_added",
      "gameIds": ["adventure", "factory"]
    }
  ],
  "operations": []
}
```

`operations` are deterministic RFC 6902 operations. They use `move`/`copy`
paths for existing args/env/hooks wherever possible so values need not appear
in output. `cutoverGameIds` names the canonical and source IDs that require
stopped-state checks. A non-empty `applicationBlocked` makes the envelope a
reviewable plan only, not a currently machine-applicable patch; the applier
must rerun/recheck against the same revision and obtain an empty blocker list.
`schemaAffectedGameIds` names every surviving entry whose future launch
semantics change because of the top-level schema bump, whether or not its entry
is directly edited; it is empty when no such bump occurs.
`wholeDocumentEffects` carries stable effect codes and exact sorted ID sets,
and is empty when there is no whole-document semantic effect. Any
editor/applier must compare `baseRevision` immediately before applying; v3
intentionally provides a revision-annotated plan, not a GABS applier or a
race-free apply guarantee.

`--format human|json-patch` and `--include-sensitive` are scoped-plan-only;
`--all` rejects them because inventory mode emits no patch. The default format
is `human`. With human output, `--include-sensitive` appends a complete
paste-ready canonical game block. With JSON Patch output, it permits necessary
materialized `add`/`replace` values when path-only `move`/`copy` operations
cannot express the plan. Both combinations warn that stdout contains config
values. MCP next actions never suggest `--include-sensitive`, and neither MCP
results nor normal logs contain the materialized values.

The same planning engine backs `profiles_not_configured`. That MCP error
contains the actual config path, requested profile, a redacted structural
preview, the exact local planner command, an empty redacted skeleton for the
requested profile, a documentation anchor, the `gabs-mcp` skill name, and
precise next actions. It never exposes existing env/hook values, invents
isolation values, or writes.

This satisfies three competing requirements at once: old configs keep working,
the common migration is almost mechanical, and GABS never guesses user intent
or mutates a launch configuration during an operational call.

## Shared implementation architecture

### `ConfigStore`

Own loading, version validation, content revisions, deep immutable snapshots,
last-known-good state, diffs, and reload health. MCP closures must not retain
the original startup config pointer.

### Launch resolver

Own pure profile selection, input validation/substitution, argument ordering,
environment sanitization/merging, working-directory selection, launch-mode
capability checks, and lifecycle resolution.

### Lifecycle manager

Own canonical per-game operation serialization, runtime claims, launch,
liveness evidence, startup/GABP monitoring, status, stop, kill, verification,
and reconciliation. MCP and CLI call this service and render its structured
results.

### Runtime store

Own schema-versioned, atomic, owner-only persistence and cross-process
operation coordination, including the bounded independent operation journal.
It must keep active removed games addressable, retain completed operations
after runtime cleanup, and handle old/corrupt snapshots explicitly.

### Process controller changes

- Extend `LaunchSpec` with resolved env, working directory, profile, config
  revision, and lifecycle metadata.
- Replace append-only `os.Environ` handling with deterministic map-based
  sanitation and merge.
- Replace launcher-PID-only assumptions with the lifecycle manager's liveness
  oracle.
- Persist and check PID birth/executable identity to avoid PID reuse.
- Provide deadline-aware workload and lifecycle-action invocation abstractions
  that can durably distinguish prepared, started, failed, and crash-ambiguous
  side effects without replay.

### MCP handler changes

- Acquire immutable config/runtime snapshots under short locks.
- Release the global server lock before filesystem/process/network waits.
- Validate all handler arguments, including unknown properties.
- Reconcile external results only after reacquiring the narrow state lock.
- Do not delete controller/runtime/bridge state before stop or kill succeeds
  and termination is verified with no unresolved action-process hazard.

## Test plan

### Backward compatibility

- Every existing unprofiled version-1.0 configuration/launch-semantics test
  stays green; the separately documented oversized public-timeout rejection is
  the one intentional call-validation exception.
- Missing/empty historical version canonicalizes to 1.0 with a warning.
- Old config and runtime files remain readable.
- Valid ordinary legacy starts receive no new profile/schema warning and remain
  observably launch-semantic compatible: same target, argv elements, effective
  non-managed env values, working directory, and lifecycle behavior. Existing
  legacy validation warnings remain unchanged.
- Schema-1.0 launches receive no `GABS_PROFILE_STATE`; schema-1.1 launches set
  it to `selected` with `GABS_PROFILE` present or `unprofiled` with
  `GABS_PROFILE` absent.
- New feature fields under version `1.0` are rejected with an upgrade action.
- Unsupported future versions are rejected.
- Existing start/connect timeout values above the new v3 maxima receive the
  documented intentional `timeout_out_of_range` result rather than overflow,
  truncation, or silent clamping.

### Config validation

- Safe/case-sensitive profile and input names.
- Maximum profile/input counts and bounded status fan-out.
- Version-1.1 ID/key grammar, path-safe legacy-ID warnings, and all-version
  base-directory containment/path-traversal rejection.
- Ambiguous target lookup returns sorted canonical-ID candidates.
- Optional valid default; missing/unknown default behavior.
- Profile override boundaries.
- Launch-input types, enums, bounds, applicability, templates, and conflicts.
- Launch-input values remain unavailable to lifecycle placeholders, and doctor
  emits the stable lifecycle-identity-neutrality contract finding with profile
  conversion guidance.
- Reserved environment prefixes, including case variants on Windows.
- `env`/`unsetEnv` conflicts, empty/invalid/NUL values, and Windows-folded
  duplicates.
- Lifecycle placeholders, exit-code sets, commands, and timeouts.
- Exact integer ranges/defaults for startup, hook, verification, caller-wait,
  recovery, and reconciliation budgets; derived exclusion-plan feasibility;
  rejection of an explicit preflight shorter than its required plan; and
  stop/kill completion-evidence policy.
- Legacy 1.0 startup timeout defaulting/large positive values remain unchanged,
  while the same over-limit config value is rejected under strict 1.1.
- Shared target/path normalization: config-directory-relative 1.1 paths,
  pinned-PATH command resolution, Windows-folded and non-Windows-exact
  comparisons, no symlink equivalence, and legacy-relative migration blockers.
- Propagation-incapable launcher-mode rejection.
- JSON-pointer diagnostics and deterministic ordering.
- Strict version-1.1 unknown-field and duplicate-JSON-key rejection.
- Initially invalid server config fails without weakening HTTP auth.

### Pure resolver

- Base/profile/input argument order.
- Environment sanitation, unsetting, precedence, and managed-variable priority.
- Launch-mode/platform-required managed variables remain final and protected.
- Profile working-directory override.
- Boolean, string, and integer substitution without shell interpretation.
- Unknown profile/input and wrong-type errors.
- Profile applicability and conflicting input bindings.
- Input-bound argv/env can change startup behavior without changing the
  snapshotted profile lifecycle identity; an identity-affecting example is
  documented as invalid configuration intent and redirected to a profile.
- Deep-copy immutability across reload.
- One pinned config revision per resolution.
- Planner and execution use the same normalized target/working-directory
  helper and absolute executable result.

### Liveness and lifecycle

- Foreground launch using tracked PID.
- Detached wrapper exits while status hook reports running; startup and GABP
  waiting continue.
- Live wrapper plus status-stopped is stopped, while live verified workload or
  GABP plus status-stopped is conflicted.
- Hook-stopped never releases an ID until GABS's own live launcher tree is
  terminated/reaped; failure remains occupied.
- Startup stopped/unknown observations settle and retry within the startup
  deadline.
- Start persists/release-probes/revalidates a bounded `preflight` before the
  locked spawn commit; running/unknown/conflicted evidence cannot spawn.
- The 128-profile/60-second status-hook boundary derives a feasible
  976-second plan; explicit shorter preflight configuration is rejected, and
  an MCP call returns an observable `preflight_pending` result after its
  20-second response slice while the accepted operation continues.
- Spawn failure, running, stopped, unknown, conflicted, and
  non-interruptible-pending rows have deterministic operation/runtime outcomes
  before attachment.
- Workload spawn commit and process verification consume one shared absolute
  `processStartDeadline`; no phase reset can double the configured budget.
- Status exits 0, 1, an unclassified code, times out, or cannot execute.
- Custom valid running/stopped/success exit-code sets.
- Unknown/conflicted evidence preserves occupancy and blocks duplicate start.
- No runtime claim plus externally running/unknown evidence remains a valid
  observable combination and blocks start without passive status writing state.
- Repeated start during `starting` or `running` returns the persisted operation
  and never creates a second process, including when requested context differs;
  boolean false normalizes to omission, unknown active profile/revision have
  distinct outcomes, externally reconstructed input names produce
  `unknown_active_inputs`, and same known-name values produce
  `unknown_value_comparison`, never a false equality claim or
  `requestedContextApplied: true`.
- Live GABP plus status-stopped produces conflict, not cleanup.
- Missing runtime probes all applicable profiles with bounded concurrency.
- Verified process environment recovers profile identity only when both
  canonical `GABS_GAME_ID`, `GABS_PROFILE_STATE=selected`, and `GABS_PROFILE`
  match; snapshot mismatch or same-profile cross-game target collision
  conflicts.
- Zero, one, and multiple externally running profiles.
- Trusted profile recovery requires every competing profile definitively
  excluded; hints never skip unknown/unprobed competitors.
- Hook-based profile attribution requires a game-and-profile-specific resolved
  status spec; a cross-game collision remains occupancy evidence only.
- Stop/kill separately reports operation acceptance, nullable action start,
  nullable action success, invocation state, and termination verification.
- Missing-snapshot stop/kill, including stop-over-preflight, owns one persisted
  recovery phase/budget before action; trusted running, stopped, failed,
  conflicted, and deadline-unknown recovery rows are deterministic and no
  attempted-launch hook is executable.
- Missing-snapshot candidates with different action/verification timeouts pin
  independent maximum-candidate allocations at acceptance; selecting a shorter
  profile never moves the hard deadline or reuses the slack.
- When only some candidates support kill/stop and evidence selects an
  unsupported one, recovery retains occupancy-only observed identity and
  terminalizes `recovered_identity_action_unsupported` without borrowing
  another hook; config repair permits a fresh recovery attempt.
- Profiled and unprofiled missing-snapshot recovery both require their exact
  trusted launch-evidence predicate; ambiguous target/process matches never
  reconstruct either.
- A live GABP session with only canonical game ID proves occupancy but cannot
  reconstruct unprofiled context after profiles are removed; verified target,
  process environment, `GABS_PROFILE_STATE=unprofiled`, and explicit
  `GABS_PROFILE` absence are required. Missing the positive state marker stays
  unknown even when `GABS_PROFILE` is absent.
- Stop-only detached wrapper succeeds under `commandExit` when no stronger
  contradictory evidence remains; `verify` requires independent evidence.
- Every stop/kill action-result x final-evidence matrix row has one terminal
  operation state; caller wait expiry alone never terminalizes it.
- Stop/kill caller wait expiry returns `termination_pending` within budget,
  exposes the persisted operation, and does not replay or forget the accepted
  action. Transport cancellation after acceptance has no response guarantee,
  but the operation continues and remains queryable by ID.
- MCP stop/kill timeout rejects zero, negative, fractional, string-valued, and
  greater-than-600-second values before accepting an operation.
- Failed stop/kill preserves controller, bridge, runtime, and profile when
  fresh liveness remains running, unknown, or conflicted; verified stopped
  cleans up despite command failure only when the action-process hazard is
  clear.
- Timed-out/failed hooks reconcile partial success and are never replayed
  automatically after restart.
- A late-started external-hook commit gets no fresh action/verification budget:
  it terminalizes immediately after durable publication with a blocking
  action-process hazard, and only a later explicit recovery may observe/reap
  the child. A late-completed built-in action instead publishes truthful
  finished/success facts with hazard clear, preserves the unverified workload
  claim, and still requires explicit recovery because no post-deadline
  liveness verification ran.
- Post-stop verification allows evidence to converge before final conflict.
- Passive status/connect/recover and pre-start discovery report strong conflict
  immediately without cleanup.
- Kill never falls back to graceful stop.
- Hook timeout cleans its process tree and bounds captured output.
- No external hook runs under the global server mutex.
- Process fingerprint rejects PID reuse.
- Unavailable fingerprints follow the documented hook/unknown fallback.
- Process-name collisions do not kill a stronger-identified process.
- Attachment covers handshake plus initial tool sync and exercises every
  connected/running/stopped/unknown/superseded row of the terminal matrix.
- CLI-deferred attachment and never-attached restart use `idle`; prior live
  connection restart uses `disconnected`; neither masquerades as `waiting`.
- Manager supersession terminalizes start/connect as `cancelled`; caller
  cancellation never does.

### Runtime and concurrency

- `runtimePhase`, operation, workload, bridge, and ownership domains cannot be
  conflated; persisted runtime-phase transitions are atomic.
- Concurrent MCP, CLI, and second-GABS operations serialize per game.
- Cross-platform advisory operation-lock acquisition/crash release and
  operation-generation invalidation survive crashes and late goroutines.
- Except for short workload/action creation commits, the advisory lock is
  released before every external wait; second start/connect, second stop/kill,
  supersession, and force-takeover join/reject rules do not replay actions.
- Workload/action commits hold the per-game/advisory lock through durable
  PID-or-failure/side-effect publication; stop/kill/takeover/forget races
  immediately before, during, and after either commit cannot create an
  unmanaged process or unrecorded lifecycle action.
- Crash injection around action `prepared`, OS invocation, `started`, and
  `finished` publication proves nullable facts and `may_have_started` recovery
  remain truthful and never replay a non-idempotent action. An orphaned
  external-hook commit has `presence_unknown`; an orphaned built-in action has
  hazard clear but action success remains unknown and fresh workload evidence
  is required.
- Live/unknown action-process hazards override workload-stopped cleanup and
  block new starts/actions until positive absence/reap or explicit
  force-forget; hook timeout and late external-hook commit cases exercise the
  same invariant. Completed built-in action commits never manufacture a child-
  process hazard.
- Kill escalates a stop only after its managed hook is cancelled/reaped and
  fresh evidence is collected; stop never supersedes kill and concurrent
  unreapable hooks are refused.
- Two simultaneous post-crash lock contenders yield one winner, and callbacks
  compare against persisted—not merely local—operation generation.
- Foreign active owner blocks lifecycle operations unless explicit takeover is
  recorded.
- Readers never observe partial runtime JSON.
- Crash injection before/between/after terminal-journal and runtime commits
  reconciles idempotently; orphaned executors resume bounded attachment or
  terminalize from evidence without replaying stop/kill.
- An orphaned `preflight` terminalizes without spawning, removes attempted
  runtime claim/authority, retains redacted attempted-launch diagnostics in
  the terminal journal, discards partial old probes, and leaves the next
  observation to use a fresh current-config snapshot.
- An orphaned stop/kill recovery phase performs no action; orphaned prepared or
  started action phases reconcile fresh evidence and never reinvoke the hook.
- Persisted operation phase, phase deadline, and hard deadline drive orphaned
  start recovery for prepared/spawn ambiguity, spawned verification, and
  attachment; no orphan phase respawns.
- Runtime and config file permissions are owner-only when GABS writes them.
- Restart/session takeover retains profile and resolved hooks.
- Profile edit/removal does not change active stop behavior.
- Removed active game remains visible and stoppable.
- Reused active ID exposes both revisions and blocks the new definition.
- Failed persistence never permits a duplicate launch.
- Old/corrupt runtime state yields safe degraded diagnostics and normal/forced
  recovery behaves exactly as specified.
- Force-forget acquires but never unlinks the stable advisory lock and refuses
  a live lock holder; it advances the persisted generation and terminally
  records cancellation before removing runtime state.
- Missing-snapshot recovery records current-config provenance and never claims
  to restore removed/original hooks.
- Missing-snapshot recovery records `appliedLaunchInputsState: unavailable`
  with no invented names; GABS-created active snapshots record the sorted
  known names, never values.
- Runtime hook snapshots exclude the inherited host environment.
- Verified stop removes active runtime state but retains a terminal journal
  record that is queryable by operation ID across restart; journal pruning
  deterministically retains the newest 32 terminal records.
- Historical operation queries label immutable finish snapshots separately
  from newly observed current status.

### Reload

- Automatic next-call pickup after in-place and atomic-replacement edits.
- A long-lived stdio/HTTP MCP connection observes valid config edits without
  server or client restart and without transport closure.
- Explicit reload returns revision and deterministic diff.
- Invalid hash is parsed once, starts are blocked, reads show stale health, and
  active stop still works.
- Fixing config automatically publishes the new snapshot.
- Added, renamed, and removed profiles.
- Active game removal.
- Hot vs startup-only top-level settings.
- Concurrent reload/calls pass the race detector.
- `tools/list` remains unchanged by profile/input edits.

### MCP

- Explicit, default, and required profile selection.
- Runtime validation of dynamic launch-input names and values.
- Root unknown-property rejection even when the client ignores schema.
- A realistic near-miss such as `timeoutSeconds` is rejected as
  `unknown_argument` with JSON path and the supported `timeout` field.
- Already-running response includes active and requested profile.
- List/show/status/start expose deterministic launch-mode and target summaries
  sufficient to distinguish similar IDs without leaking argv/env/hooks.
- Two same-mode path targets with the same basename receive shortest-unique
  suffix labels and distinct stable target fingerprints.
- Start/status keep operation, workload, and bridge phases separate and include
  retry timing/deadlines for pending background preflight, spawn commit,
  process verification, and attachment; timeout ties return terminal results
  unless the non-interruptible spawn exception still owns the commit.
- Start attachment expiry distinguishes verified-running bridge-unavailable,
  verified-stopped, and occupied-unverified outcomes.
- Connect joins an existing waiting attachment, bounds only that caller's wait,
  and retries unavailable/disconnected state without relaunch or profile change.
- A connected start points directly to discovery and never recommends a
  redundant connect.
- Discovery exposes schemas but not templates or supplied values.
- Stable structured errors and actionable next actions.
- Active-profile reporting across start/status/connect/stop/kill.
- Status/stop/kill expose action-process hazard, evidence, `releaseSafe`, and
  exact positive-recovery/local-force clearing actions.
- Recovery profile hints require confirming evidence; force takeover is explicit.
- Stop/kill without a snapshot must persist the shared recovery transition
  before executing any current-config lifecycle hook.
- MCP mapping previews remain redacted and `games_recover` never force-forgets.
- Every core handler rejects root unknown properties independently of schema
  enforcement, and every timeout tie follows the terminal-record-first rule.

### CLI and mapping

- Per-action flag parsing, typed repeated inputs, and duplicate-name errors.
- CLI/MCP resolver and lifecycle parity.
- Start exits without retaining a redundant GABP client.
- Status/stop/kill from a persisted snapshot.
- Standalone stop/kill waits to a terminal internal result and exposes no
  caller-only timeout flag or managerless pending continuation.
- A simulated non-interruptible workload/action commit keeps the standalone
  CLI resident through durable publication, while forced termination leaves a
  recoverable prepared state rather than a false completed/absent claim.
- Normal and force-forget recovery paths.
- Missing/duplicate/canonical-as-source arguments, duplicate/colliding profile
  names, already-profiled entries, invalid `--target`, and acknowledgement/flag
  misuse fail deterministically before plan emission.
- Duplicate JSON object members block every planner patch path, including
  no-schema-bump exact deduplication of legacy 1.0 entries; a raw hash never
  substitutes for unambiguous JSON Pointer semantics.
- Adjacent `--from-game ID --as-profile NAME` parsing remains unambiguous for a
  path-safe legacy ID containing `=`.
- A profile-producing plan strict-validates the entire proposed 1.1 document;
  unrelated blockers return `schema_upgrade_blocked` with no patch or repair.
- `--all` labels profiled entries `already_profiled`; planner v1 never flattens
  or compares profile sets.
- Default canonical-profile creation preserves omitted start; explicit-profile
  behavior requires `--require-explicit-profile`.
- Bare duplicates associate with exactly one selected output context class.
- Target-only normalization accepts a bare source that becomes exact under the
  explicit target as deduplication. A named source that becomes exact remains
  rejected unless `--canonical-profile`, `--target`, and
  `--accept-profile-name-contract` deliberately select the name-only wrapper
  path; that path creates the distinct profiles, reports
  `unproven_profile_name_contract`, and never claims resolver equivalence.
- `--accept-profile-name-contract` without a target-normalized named source is
  rejected; its valid planning path requires the single-instance
  acknowledgement, common launch inputs, and a propagation-capable canonical
  launch mode. Active/unknown cutover IDs still produce the revision-bound
  plan with `applicationBlocked: cutover_ids_not_verified_stopped`, but
  application waits for an immediate stopped-state recheck and completion
  waits for doctor plus sequential start/status/stop acceptance of every
  generated profile.
- Same-identity context variants under a propagation-incapable mode are
  `same_identity_profile_ineligible`; exact duplicates may still deduplicate.
- Identical normalized launch-input declarations remain common at game level;
  added/removed/changed declarations produce
  `launch_input_consolidation_blocked`, never an implicit union, source choice,
  or profile applicability broadening.
- `${gameId}`/`${id}` hook templates compare symbolically for grouping while
  actual expansion changes remain reported cutover effects; cross-ID matches
  receive only `equivalent_except_for_id_cutover`, never an unqualified
  resolver-equivalent verdict.
- Default planning performs no hook or state action; `--probe-status` may run
  bounded observational hooks but never reconciles/persists state.
- `--all` rejects scoped output/sensitive flags; both human and JSON Patch
  sensitive-output combinations warn and remain revision-bound.
- Plans report and require acknowledgement of collapsed per-ID concurrency,
  mirrored namespace/script-reference changes, and managed identity cutover.
- Single-entry mapping plan preserves resolver behavior modulo listed managed
  profile-state metadata.
- Single-entry freeze reports exact source-version deltas: 1.0 has
  `GABS_PROFILE_STATE` absent -> selected, while 1.1 has unprofiled -> selected;
  both add `GABS_PROFILE`.
- A profile-producing top-level schema upgrade lists the
  `GABS_PROFILE_STATE=unprofiled` effect for every untouched unprofiled entry;
  it neither wraps those entries nor calls their full environment identical.
  JSON Patch output separates lifecycle-sensitive `cutoverGameIds` from every
  surviving `schemaAffectedGameIds` entry and supplies exact
  `wholeDocumentEffects`; an already-1.1/no-schema-bump plan leaves untouched
  entries unchanged and emits empty schema-effect fields.
- `profiles plan --all` deterministically classifies exact duplicates, profile
  candidates, and separate identities through identity groups and
  mutable-context equivalence classes without emitting a patch.
- Ordinary/non-target-normalized exact duplicates produce a deduplication plan
  with no redundant profiles; meaningful mutable-context differences require
  explicit profile names, and naming an ordinary exact duplicate as a profile
  is rejected. The acknowledged target-normalized name-only wrapper path is
  the sole exception.
- Mixed scoped plans can remove bare exact duplicates while importing named
  context variants, with `--canonical-profile` required exactly when the
  canonical launch must become a profile.
- The closed immutable comparison set and mode-aware target normalization are
  deterministic across CLI and MCP planner views.
- One multi-source consolidation plan covers canonical and imported profiles.
- Incompatible identity diff refuses consolidation.
- Planner reports active sources as unsafe and emits a single-edit,
  revision-annotated source-removing plan with
  `applicationBlocked: cutover_ids_not_verified_stopped`, without claiming
  current machine applicability or atomic/race-free application.
- Mapping command never writes; CLI output is revision-annotated and
  machine-applicable only after the prescribed revision, collision, and
  stopped-state rechecks, while MCP output is deterministic and redacted.

### End-to-end acceptance

Use neutral helper launchers and temporary directories:

1. configure one canonical game with two profiles and a declared quick-start
   input;
2. launch the first profile and verify argv/env/cwd and output isolation;
3. verify active profile and applied-input names in status;
4. stop through its configured hook and verify termination;
5. launch the second profile without restarting GABS or the MCP client;
6. run a detached-wrapper variant whose launcher exits while status remains
   running;
7. edit/rename a profile, verify automatic and explicit reload, and launch the
   new definition;
8. invalidate config while a launch is active, prove new starts are blocked,
   then stop the active launch from its snapshot;
9. restart GABS between launch and stop and prove recovery remains correct;
10. delay bridge readiness beyond the initial start wait, verify the pending
    operation/workload/bridge phases and next action, then attach without a
    second launch; and
11. delay termination beyond an MCP caller wait budget, verify bounded
    `termination_pending`, then observe final reconciliation by operation ID;
    separately verify standalone CLI stop waits to its terminal internal
    deadline rather than abandoning a managerless continuation.

## Implementation sequence

Treat this as a substantial architecture release and keep it reviewable through
independently mergeable milestones:

1. **Schema and resolution:** introduce version-1.1 types, full validation,
   deterministic revisions, environment handling, pure profile/input resolver,
   discovery, and profile-aware MCP start plumbing.
2. **Lifecycle correctness:** add atomic private runtime snapshots, the stable
   operation lock/generation model, transport-neutral lifecycle manager,
   liveness oracle, detached startup/GABP monitoring, stop/kill verification,
   and normal/forced recovery.
3. **Live configuration and diagnostics:** replace captured startup config
   pointers with `ConfigStore`, add automatic/explicit reload, strict handler
   validation, profile-aware MCP doctor/recover, and active-definition health.
4. **CLI and migration:** move lifecycle commands onto the shared manager,
   extend the existing CLI doctor, and add the revision-bound non-writing
   multi-source profile planner.
5. **Delivery:** update neutral docs/examples, repo-owned skill and install/check
   hook, then run unit, race, acceptance, security, genericity, build, and
   installed-skill checks.

Milestone 1 is not issue completion: the sender's wrapped/detached stop
requirement depends on milestone 2. The milestones control regression risk;
they do not reduce final acceptance.

Do not implement lifecycle hooks only inside `games_status`/`games_stop`, add a
reload parser while handlers still capture the startup config pointer, or add
CLI commands by duplicating MCP logic. Those partial implementations would
look complete in simple tests while failing the detached, concurrent, and
cross-session cases that make this feature necessary.

## Final acceptance criteria

The feature is complete only when all of the following are true:

- the issue sender can deduplicate exact launch duplicates, convert
  same-identity entries with distinct launch contexts into named profiles, or
  explicitly normalize near-identical wrappers to one chosen canonical
  launcher—including the acknowledged name-only profile contract when old
  target paths carried all context—and stop the correct wrapped/containerized
  profile;
- the quick-start request is possible through a declared, lifecycle-neutral
  typed input without exposing arbitrary args/env, while any value needed to
  identify or stop the workload is modeled as profile context;
- existing unprofiled configurations and ordinary starts remain observably
  launch-semantic compatible;
- profile adoption has a deterministic, non-writing mapping path that
  distinguishes exact deduplication, same-identity variants, and different
  identities, blocks ambiguous/different game-level launch-input declarations,
  validates the whole upgraded document, and reports/acknowledges lost per-ID
  concurrency, namespace/script-reference cutovers, and whole-document schema
  launch effects;
- detached launch liveness remains correct after the wrapper exits;
- a declared stop-only wrapped launch can complete under its explicit/default
  command-exit evidence policy, while contradictory live evidence still wins;
- every non-cancelled MCP start/connect/stop/kill/recover call with an available
  response channel returns within a documented caller bound, while transport
  cancellation makes no delivery promise; standalone CLI operations wait to
  their finite internal deadline, with only an already in-flight
  non-interruptible side-effect commit allowed to overrun until durable
  publication; every accepted continuing operation remains visible by ID with
  exact next actions;
- config edits are visible without client/server restart and can be explicitly
  verified;
- unknown MCP/CLI arguments are rejected structurally rather than ignored;
- lifecycle failures and contradictory evidence never discard live state or
  authorize duplicates;
- unknown/corrupt coordination state has a supported evidence-first recovery
  path without hand-editing internal files;
- a GABS restart or config edit does not lose the selected profile or safe stop
  behavior;
- MCP and CLI produce the same decisions from the same snapshots;
- same-basename installations remain distinguishable before start through
  collision-aware identity summaries;
- public surfaces remain generic, discoverable, stable, and deterministic; and
- the installed `gabs-mcp` skill matches the repository source.
