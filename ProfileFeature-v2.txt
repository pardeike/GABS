# GABS Launch Profiles — Design v2

Resolves issue #66 (https://github.com/pardeike/GABS/issues/66): launch the same
game under named, isolated launch contexts; let users opt into pre-declared
startup options; make wrapped/containerized launches controllable; and make
config edits effective without restarting GABS or the MCP client.

## Goals

1. `games_start` with `profile: "combat-test"` launches one configured game
   under a named launch context, with nothing bleeding into other profiles.
2. Users can request declared startup options ("start with quickstart") without
   GABS ever exposing raw argument/environment passthrough to the AI.
3. Wrapped and containerized launches get working status/stop/kill via
   configured commands (host-side `stopProcessName` cannot see into containers).
4. Editing config takes effect on the next call — no GABS or client restart.

## Non-goals

- Game-specific concepts such as `dataDir`. Isolation is expressed through
  generic args/env/workingDir; enforcement belongs to the launcher, wrapper, or
  container.
- Raw per-call args/env overrides on the MCP surface.
- Multiple concurrent instances of one game ID (separate installations or
  simultaneous instances remain separate game IDs).
- Automatic migration or rewriting of existing configs.

## Design principles

- **Discoverable, not documented-only**: everything an agent can pass to
  `games_start` is described by `games_show`; no step requires reading the
  config file.
- **JSON-Schema vocabulary**: launch options use `type`, `enum`, `minimum`,
  `maximum` — the vocabulary AI models and MCP clients already know.
- **No procedure to remember**: config reload is automatic; stop/kill reuse the
  profile chosen at launch; there are no new tools and `tools/list` never
  changes.
- **Fail at validation time, not start time**: configuration mistakes surface
  when the config is loaded, with the exact error; a valid config never
  produces a "you forgot a parameter" start failure.
- **Errors state the next action**: a self-describing error code, the facts,
  and a documentation anchor — not generated migration recipes.

## Configuration schema

All new fields are optional additions to the existing game entry; config
version stays `1.0` and existing configs remain valid and untouched.

```json
{
  "id": "adventure",
  "name": "Adventure Game",
  "launchMode": "DirectPath",
  "target": "/games/adventure/launch",
  "args": ["--bridge"],
  "env": { "LOG_FORMAT": "json" },
  "defaultProfile": "vanilla",
  "profiles": {
    "vanilla": {
      "description": "Isolated vanilla data",
      "args": ["--data-dir", "/srv/adventure/vanilla"]
    },
    "combat-test": {
      "description": "Isolated combat-test data",
      "args": ["--data-dir", "/srv/adventure/combat-test"],
      "env": { "PROFILE_DATA": "/srv/adventure/combat-test" }
    }
  },
  "launchOptions": {
    "quickStart": {
      "description": "Skip menus and load straight into the quick-start path",
      "type": "boolean",
      "args": ["--quick-start"]
    },
    "scenario": {
      "description": "Select a configured startup scenario",
      "type": "string",
      "enum": ["arena", "tutorial"],
      "args": ["--scenario", "${value}"]
    }
  },
  "lifecycle": {
    "status": { "command": "containerctl", "args": ["is-running", "adventure-${profile}"] },
    "stop":   { "command": "containerctl", "args": ["stop", "adventure-${profile}"] },
    "kill":   { "command": "containerctl", "args": ["kill", "adventure-${profile}"] }
  }
}
```

New game-level fields: `env`, `defaultProfile`, `profiles`, `launchOptions`,
`lifecycle`.

### Profiles

- A profile is a launch-context overlay: `description`, `args`, `env`,
  `workingDir`, and per-hook `lifecycle` overrides. It cannot change identity
  or transport: `id`, `name`, `target`, `launchMode`, `stopProcessName`,
  `gabpMode`, and bridge identity stay at game level.
- `workingDir` is overridable per profile because per-profile working
  directories are a natural isolation mechanism for games that write relative
  to their cwd.
- When `profiles` is non-empty, `defaultProfile` is **required** and must name
  a configured profile — enforced at validation time. Consequence:
  `games_start <id>` without a profile always works, exactly as it does for
  unprofiled games.
- Exactly one profile can be active per game ID at a time.
- Games without `profiles` keep their current behavior bit-for-bit.

### Launch options

The "start with quickstart" request from issue #66, made safe by declaration:
the config author declares named, typed options; agents may supply only those
names and values. The name deliberately echoes Steam's "launch options", which
is what users expect this to be.

- Types: `boolean`, `string`, `integer`. Strings may declare `enum`; integers
  may declare `minimum`/`maximum`. An optional `profiles` array restricts an
  option to specific profiles.
- Each option carries its own `args` and/or `env` mapping. `${value}` in those
  templates is replaced by the supplied value. A boolean option applies its
  mapping only when supplied as `true`; `false` is equivalent to omitting it.
- Options are applied only when the caller explicitly supplies them. There are
  no implicit defaults — an unmentioned option never affects a launch.

### Lifecycle hooks

Structured commands replace the shell-string `stopCommand` from the issue:

- Hooks: `status`, `stop`, `kill`. Each supports `command` (required), `args`,
  `workingDir`, `env`, and `timeoutSeconds` (defaults: 5 for status, 30 for
  stop, 10 for kill).
- Execution is exact executable-plus-argv — never shell interpretation. Users
  who need pipelines or shell syntax wrap them in a script and configure that.
- Placeholders `${gameId}` and `${profile}` are substituted in `args` and `env`
  values. `${profile}` is valid only for games that define profiles (and then
  always resolves, since `defaultProfile` is required). Unknown placeholders
  are validation errors.
- Exit-code contract, fixed and knob-free:
    - status: exit 0 = running; any other exit = stopped; timeout or failure to
      execute = unknown.
    - stop/kill: exit 0 = success; anything else = failure.
  Tools with exotic exit conventions get a wrapper script, not config options.

### Validation rules

- Environment keys under the reserved `GABS_` and `GABP_` prefixes are rejected
  everywhere (game, profile, option, hook). GABS stays authoritative for bridge
  and profile metadata.
- `SteamAppId` and `EpicAppId` launch via launcher URLs and cannot propagate
  configured args/env; profiles or launch options that define `args` or `env`
  are validation errors for those modes (pointing at SteamManaged, DirectPath,
  or CustomCommand). Lifecycle hooks work with every launch mode.
- Reference mistakes — unknown `defaultProfile`, an option's `profiles` listing
  an undefined profile, bad placeholders, contradictory `enum`/`minimum`/
  `maximum` — are validation errors reported at config load with exact
  positions.

## Worked example: separate installations

Consider two installations of the same game: `adventure-store` (SteamManaged,
with a configured launch argument) and `adventure-legacy` (DirectPath into a
standalone installation, with its own data-directory argument). Under this
design:

- The two entries correctly **remain separate game IDs**: they differ in
  launch mode and target — identity, not launch context. The rule "profiles
  overlay context, never identity" is exactly the line between them.
- What genuinely varies per context is the data directory, so each entry gains
  profiles for that:

```json
{
  "id": "adventure-store",
  "name": "Adventure Game (Store)",
  "launchMode": "SteamManaged",
  "target": "123456",
  "args": ["--safe-rendering"],
  "stopProcessName": "AdventureGame",
  "defaultProfile": "vanilla",
  "profiles": {
    "vanilla": {
      "description": "Untouched user data",
      "args": ["--data-dir=/srv/adventure/vanilla"]
    },
    "integration-test": {
      "description": "Isolated integration-test data",
      "args": ["--data-dir=/srv/adventure/integration-test"]
    }
  }
}
```

- `SteamManaged` launches the resolved executable directly, so args/env-based
  profiles work here; only the `SteamAppId`/`EpicAppId` URL modes reject them.
- Other standalone versions each become one DirectPath game ID per version — a
  different target each — carrying the same per-version profile pattern.
- The configured `--data-dir=<path>` argument is precisely the generic-args
  isolation mechanism the design relies on; no game-specific `dataDir` concept
  is needed.

## Launch resolution

A pure resolver takes (immutable game snapshot, profile name, option values)
and produces a resolved process spec plus a resolved lifecycle snapshot. All
maps and slices are deep-copied so later config reloads can never mutate an
active launch.

- Argument order: game `args`, then profile `args`, then supplied option arg
  groups sorted by option name (deterministic and easy to reason about).
- Environment precedence (later wins): inherited process environment → game
  `env` → profile `env` → supplied option `env` mappings → GABS-managed
  variables (`GABS_GAME_ID`, `GABP_*`, `GABS_PROFILE`).
- Working directory: profile `workingDir` if set, else game `workingDir`.
- `GABS_PROFILE=<name>` is exported to the launched process and to lifecycle
  hook commands whenever a profile is selected; it is unset for unprofiled
  games. `GABS_GAME_ID` and the GABP endpoint variables are unchanged, so no
  GABP wire-version change is needed.

## Lifecycle semantics

- Per-hook resolution order: profile override → game-level hook → existing
  built-in behavior (tracked PID, then `stopProcessName`).
- A configured status hook is authoritative for detached or wrapped launches.
  An `unknown` result (timeout/exec failure) preserves runtime state and
  reports a diagnostic — it is never treated as stopped and never triggers
  cleanup.
- After a stop/kill hook succeeds, GABS polls the status hook until it reports
  stopped or the hook timeout expires. Without a status hook, the stop/kill
  command's success is the termination evidence.
- A failed lifecycle command preserves controller, runtime, bridge, and profile
  state so the operation can be diagnosed and retried.
- `games_kill` uses the kill hook or the existing host-process kill. It never
  silently substitutes the graceful stop hook; if no force-capable action
  exists, it says so.

## Automatic config reload

- GABS keeps an immutable, concurrency-safe config snapshot. On every
  config-dependent call it re-hashes `config.json` and parses/publishes a new
  snapshot only when the content hash changed. This needs no filesystem
  watchers and catches atomic rename-based saves.
- Hot vs. startup-only is one crisp line: everything under `games` (profiles,
  options, hooks included) is hot; top-level settings (`apiKey`,
  `toolNormalization`, `portRanges`, `timeouts`, `stripOutputSchema`) are read
  at startup and documented as requiring a restart.
- Invalid config: keep the last valid snapshot. New starts are refused with the
  exact parse/validation error; read-only calls succeed with a visible
  stale-config diagnostic; connect/stop/kill of active launches keep working
  from their launch snapshots.
- If a reload removes or renames an active game, it stays addressable under its
  original ID (reported as `configured: false`) for status/stop/kill; a live
  bridge/runtime is never reassigned to a new ID.
- `tools/list` never changes from profile/option edits — that metadata lives in
  `games_show` results, so no client restarts and no surface churn.
- There is **no reload tool**. The verification loop after an edit is simply:
  edit config → `games_show <id>` → the new state (or the exact error) is
  right there.

## MCP surface

No new tools; the stable core surface is unchanged.

- `games_start` gains `profile?: string` and `launchOptions?: object`
  alongside `gameId`, `timeout`, `resetEndpoint`. The schema is strict: raw
  override-like fields (`args`, `env`, `extraArgs`, …) are rejected, not
  ignored. Tool description states that launch options are startup-only values
  the user must explicitly request and the config must already declare — never
  a substitute for GABP tools.
- Start results report `activeProfile` and the **names** of applied options,
  never their values. Starting profile B while profile A is active returns the
  existing already-running result augmented with `activeProfile` and
  `requestedProfile`; it never starts a second instance.
- `games_show` returns sorted profile names with descriptions, the default
  profile, and launch options as a JSON-Schema-style map (name → `type`,
  `description`, `enum`, `minimum`, `maximum`, applicable `profiles`). The
  underlying args/env templates are not exposed to the AI-facing result.
- `games_list` keeps its compact text output; structured content adds
  `defaultProfile` and profile names per game.
- `games_status`, `games_connect`, `games_stop`, and `games_kill` report the
  active profile when known. Stop/kill act on the profile and lifecycle
  snapshot stored at launch — callers never repeat or guess the profile.
- Requesting a profile on a game without profiles returns a structured,
  non-executing error: code `profiles_not_configured`, the game ID, requested
  profile, actual config path, a documentation anchor for launch profiles, and
  a note that edits take effect without restarting. GABS does not generate a
  migration recipe and never rewrites the user's config.

## CLI surface

New lifecycle commands share the resolver, validation, runtime state, and
profile semantics with MCP:

```
gabs games start <id> [--profile NAME] [-o NAME=VALUE]... [--timeout SECONDS] [--reset-endpoint]
gabs games status [<id>]
gabs games stop <id>
gabs games kill <id>
```

- Repeated `-o/--option` values are parsed according to the declared option
  type.
- `start` prepares the normal endpoint/runtime state and verifies startup, but
  does not keep a redundant GABP client alive after the CLI exits; an MCP GABS
  process attaches later through the normal `games_connect` path.
- `status`/`stop`/`kill` operate from the persisted launch snapshot, including
  after the original launcher or GABS process has exited.

## Runtime state

- `runtime.json` gains: selected profile, config revision, applied option
  names, and the resolved status/stop/kill command snapshots. Option values and
  resolved environment values are never persisted and never logged.
- One runtime path and one bridge identity per game ID, as today.
  `runtime.json` stays GABS-owned lifecycle state; the game-side bridge keeps
  using the live `GABP_SERVER_PORT`, `GABP_TOKEN`, and `GABS_GAME_ID` process
  environment.

## Documentation and skill

- CONFIGURATION.md gets the full schema reference with a neutral
  game/container example; README, INTEGRATION, and the dynamic-tools guide get
  short touch-ups; `example-config.json` gains one profiled game. Run the
  existing public-surface genericity scan over all public docs and examples.
- The repo-owned `gabs-mcp` skill gains concise guidance: prefer named
  profiles over duplicated game IDs when target/launch mode are the same; pass
  launch options only when the user explicitly asks for that declared option;
  never invent options or use them to rebuild a control channel that belongs in
  GABP tools; config edits are picked up automatically — verify with
  `games_show`; stop/kill without guessing the profile. Detailed schema
  examples stay in CONFIGURATION.md, not SKILL.md.

## Test plan

- **Baseline**: all existing tests for unprofiled configs stay green,
  unchanged.
- **Validation**: default-profile requirement, profile/option reference errors,
  reserved env prefixes, placeholder validation, launcher-URL-mode rejection,
  backward-compatible serialization.
- **Resolver**: argument ordering, env precedence, workingDir override,
  boolean/string/integer options with `enum`/`minimum`/`maximum`, unknown
  profiles/options, rejection of raw override fields, deep-copy immutability.
- **Lifecycle**: neutral helper scripts covering foreground and detached
  launches, the fixed exit-code contract, timeouts, unknown-state preservation,
  stop→status polling, kill-vs-stop priority, command failure preserving state,
  absence of shell interpretation.
- **MCP**: explicit/default profile starts, duplicate-profile start returns
  already-running with both profiles, metadata exposure without templates or
  values, strict-schema rejection, `profiles_not_configured` error shape.
- **Reload**: next-call pickup after atomic replacement, added/renamed
  profiles, invalid-file last-good behavior with blocked starts and working
  stop, removal of an active game, unchanged `tools/list`; concurrent
  reload/call tests under `-race`.
- **CLI**: `--profile`, repeated typed `-o`, default profile, status/stop/kill
  from persisted snapshots, parity with MCP resolution.
- **Acceptance**: two profiles pointing at separate temp data directories;
  launch each sequentially under one game ID; verify args/env/output stay
  inside the selected directory and the active profile shows in status; stop
  via the configured hook; rename a profile on disk; launch the renamed profile
  — all without restarting GABS or the client.
- **Gates**: `go test ./...`, `go test -race ./...`, `make build`, genericity
  scan, clean working tree.

## Out of scope (follow-ups, not part of this change)

- Skill install tooling (`scripts/install-skills.sh`, drift check between repo
  and installed skill) — a separate repo chore, tracked independently.
- Automatic conversion of existing per-profile game IDs into profiles.
- Concurrent instances of one game ID.

## Assumptions

- Profiles are launch-context overlays, not embedded sub-games; GABS selects
  and transports profile context, while filesystem/container isolation remains
  the launcher/game integration's responsibility.
- Existing `stopProcessName` behavior remains a supported fallback.
- Ordinary legacy starts remain backward compatible and warning-free.
