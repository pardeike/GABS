• Proposed Plan


  # Resolve GABS Issue #66 with Profiles, Declared Launch Inputs, Lifecycle Hooks, and Live
  Config Reload

  ## Summary

  - Address GABS issue #66 (https://github.com/pardeike/GABS/issues/66) with a three-layer
    model: stable game identity → named launch profile → explicitly declared launch inputs.

  - Keep one active profile per game ID. Different installations or launch modes remain
    separate game IDs; profiles represent isolated launch contexts beneath one target.

  - Do not add game-specific concepts such as dataDir. Isolation is expressed through
    generic arguments/environment and enforced by the game, wrapper, or container.

  - Do not expose raw per-call arguments or environment variables to MCP. Configuration
    authors declare typed, named inputs; agents may supply only those names and values.

  - Replace the proposed shell-style stopCommand string with structured, cross-platform
    status, stop, and kill commands.

  - Add automatic config reload plus an explicit games_reload_config tool, so profile/config
    edits become visible without restarting GABS or the Codex session.

  - Preserve existing configs unchanged. A profile request against an old game entry is
    rejected with an exact manual conversion recipe, documentation link, installed-skill
    guidance, and reload/retry steps; GABS never rewrites the config automatically.

  ## Public Configuration and Interfaces

  ### Profile and launch-input schema

  Extend each game with optional env, defaultProfile, profiles, launchInputs, and lifecycle
  fields:

  {
    "id": "adventure",
    "name": "Adventure Game",
    "launchMode": "DirectPath",
    "target": "/games/adventure/launch",
    "args": ["--bridge"],
    "env": {
      "LOG_FORMAT": "json"
    },
    "defaultProfile": "vanilla",
    "profiles": {
      "vanilla": {
        "description": "Isolated vanilla data",
        "args": ["--data-dir", "/srv/adventure/vanilla"],
        "env": {
          "PROFILE_DATA": "/srv/adventure/vanilla"
        }
      },
      "combat-test": {
        "description": "Isolated combat-test data",
        "args": ["--data-dir", "/srv/adventure/combat-test"],
        "env": {
          "PROFILE_DATA": "/srv/adventure/combat-test"
        }
      }
    },
    "launchInputs": {
      "quickStart": {
        "description": "Enable the configured quick-start path",
        "type": "boolean",
        "args": ["--quick-start"],
        "profiles": ["combat-test"]
      },
      "scenario": {
        "description": "Select a configured startup scenario",
        "type": "string",
        "allowedValues": ["arena", "tutorial"],
        "args": ["--scenario", "${value}"]
      }
    },
    "lifecycle": {
      "status": {
        "command": "containerctl",
        "args": ["is-running", "adventure-${profile}"],
        "timeoutSeconds": 5
      },
      "stop": {
        "command": "containerctl",
        "args": ["stop", "adventure-${profile}"],
        "timeoutSeconds": 30
      },
      "kill": {
        "command": "containerctl",
        "args": ["kill", "adventure-${profile}"],
        "timeoutSeconds": 10
      }
    }
  }

  - Game-level args and env are common launch context. Profile arguments append to base
    arguments; profile environment overrides matching base environment keys.

  - Profiles may define fixed args, env, and per-hook lifecycle overrides. They may not
    replace the game ID, name, target, launch mode, working directory, stopProcessName, GABP
    mode, or bridge identity.

  - defaultProfile must name a configured profile. If profiles exist and a start omits
    profile, use defaultProfile; if none is configured, reject the start and list the
    available profiles.

  - Existing games without profiles retain their current unprofiled behavior exactly.
  - Launch-input types are boolean, string, and integer. String inputs may use
    allowedValues; integer inputs may use minimum and maximum.

  - A supplied boolean input applies its mapping only when true. String and integer values
    replace ${value} in that input’s configured arguments/environment.

  - Launch inputs may optionally list the profiles for which they are valid. No defaults are
    applied implicitly; an input affects a launch only when the caller explicitly supplies
    it.

  - Effective argument order is base arguments, selected-profile arguments, then supplied
    launch-input argument groups ordered lexically by input name.

  - Environment precedence is inherited process environment → game env → profile env →
    supplied named-input mappings → GABS-managed variables.

  - Reject configured environment keys under the reserved GABS_ and GABP_ prefixes. GABS
    remains authoritative for bridge and profile metadata.

  - Pass GABS_PROFILE=<selected-name> to the launch and lifecycle commands while leaving
    GABS_GAME_ID and the existing GABP endpoint variables unchanged.

  - Lifecycle command placeholders are ${gameId}, compatibility alias ${id}, and ${profile}.
    Unknown or unavailable placeholders are configuration errors.

  - Lifecycle commands use exact executable-plus-argv execution, never implicit shell
    parsing. Each command supports command, args, workingDir, env, and timeoutSeconds; users
    needing pipelines or shell syntax must explicitly configure a wrapper executable.

  - Status commands default to exit code 0 = running, 1 = stopped, and any other code,
    timeout, or execution failure = unknown. Optional runningExitCodes and stoppedExitCodes
    may override those sets. Stop and kill commands default to exit code 0 = success, with
    optional successExitCodes.

  - Default command timeouts are 5 seconds for status, 30 seconds for stop, and 10 seconds
    for kill.

  - For legacy launcher URL modes that cannot propagate configured launch arguments/
    environment, reject profile or launch-input configurations that depend on those fields
    and direct users to SteamManaged, DirectPath, or CustomCommand. Lifecycle hooks remain
    usable with every launch mode.

  - Keep the existing top-level config schema version compatible; all new fields are
    optional and existing version 1.0 configs remain valid.

  ### MCP surface

  - Extend games_start with:
      - profile?: string
      - launchInputs?: object
      - existing gameId, timeout, and resetEndpoint

  - Do not add extraArgs, args, env, or any raw-override block to the MCP schema. Reject
    rather than silently ignore undeclared override-like fields.

  - Describe launchInputs as startup-only values that must be explicitly requested by the
    user and must already be declared by the game configuration. Never suggest them as
    substitutes for GABP tools.

  - games_show returns sorted profile names, default profile, profile descriptions, and the
    names/types/descriptions/constraints of applicable launch inputs. It does not expose the
    underlying argument/environment templates to the AI-facing structured result.

  - games_list keeps its compact game-ID text output while adding profile availability/
    default information to structured content.

  - games_status, games_connect, games_start, games_stop, and games_kill report the active
    profile when known. Start results report only the names of applied launch inputs, never
    their values.

  - Starting profile B while profile A is already active returns the existing “already
    running” result augmented with activeProfile and requestedProfile; it never starts a
    second instance.

  - games_stop and games_kill use the profile and resolved lifecycle snapshot stored at
    launch. Callers do not need to repeat the profile.

  - Add stable core tool games_reload_config, returning changed, configuration revision,
    added/updated/removed game IDs, active removed IDs, validation warnings, and any
    startup-only fields that still require a process restart.

  ### CLI surface

  Add lifecycle commands using the same resolver, validation, runtime state, and profile
  semantics as MCP:

  gabs games start <id> [--profile <name>] [--input <name>=<value>]... [--timeout <seconds>]
  [--reset-endpoint]
  gabs games status [<id>]
  gabs games stop <id>
  gabs games kill <id>

  - Parse repeated --input values according to the declared input type.
  - CLI start prepares the normal endpoint/runtime state and verifies process or configured
    status, but does not keep a redundant GABP client alive after the CLI exits; an MCP GABS
    process can attach through the normal games_connect path.

  - CLI status/stop/kill work from the persisted active-launch snapshot, including after the
    original launcher process or GABS process exits.

  ## Runtime, Lifecycle, Reload, and Legacy Mapping

  - Introduce a pure launch resolver that accepts an immutable game snapshot, optional
    profile, and declared input values and produces a resolved process specification plus
    resolved lifecycle hooks. Clone all maps/slices so later config reloads cannot mutate an
    active launch.

  - Extend the process launch specification with resolved environment and profile metadata.
  - Extend runtime.json with the selected profile, configuration revision, applied launch-
    input names, and resolved status/stop/kill command snapshots. Do not persist named-input
    values or launch environment values, and do not log them.

  - Continue using one runtime path and one bridge identity per game ID. runtime.json
    remains GABS-owned lifecycle state; the game-side bridge continues to use the live
    GABP_SERVER_PORT, GABP_TOKEN, and GABS_GAME_ID process environment.

  - Lifecycle resolution order is selected-profile hook → game-level hook → existing PID/
    stopProcessName behavior.

  - A configured status hook is authoritative for detached/wrapped launches. A timeout or
    unknown result preserves runtime state and reports diagnostics rather than incorrectly
    cleaning it as stopped.

  - After a successful stop/kill hook, poll the status hook until it reports stopped or the
    command timeout expires. Without a status hook, successful completion of the stop/kill
    command is the termination evidence.

  - A failed lifecycle command preserves controller, runtime, bridge, and profile state so
    the operation can be diagnosed or retried.

  - games_kill uses the configured kill hook or existing host-process kill. It must not
    silently substitute the graceful stop hook when no force-capable action exists.

  - Add an immutable, concurrency-safe config store. On every config-dependent MCP call,
    read/hash config.json; only parse and publish a new snapshot when its content revision
    changes. This avoids filesystem-watcher dependencies and catches atomic rename-based
    saves.

  - games_reload_config forces the same load path and makes the resulting revision/diff
    visible immediately.

  - On malformed or invalid config, retain the last valid snapshot:
      - refuse new starts so stale launch data is not used;
      - continue read-only status/discovery with a visible stale-config diagnostic;
      - continue connect/stop/kill for active launches from their persisted snapshots;
      - let games_reload_config return the exact parse/validation error.

  - Hot-reload game definitions, profiles, launch inputs, lifecycle hooks, port ranges,
    startup/session timeouts, and output-schema stripping. Treat API-key and tool-name-
    normalization changes as startup-only and report them as such.

  - Do not rebuild or mutate tools/list for profile/input changes. Their metadata comes from
    games_show, preserving the stable core surface and avoiding client/Codex restarts.

  - If an active game is removed or renamed by reload, retain it as configured: false, keep
    it addressable by its original ID in status/stop/kill, and warn in the reload result.
    Never reassign a live bridge/runtime to the new ID.

  - Keep old entries valid for ordinary unprofiled starts. If games_start requests a profile
    for a game with no profiles, return a structured non-executing result with:
      - code profiles_not_configured;
      - requested profile, game ID, and actual config path;
      - the existing game-level args and env;
      - a conservative manual recipe that moves all existing args/env into a suggested
        current default profile while leaving identity, target, launch mode, working
        directory, process tracking, and bridge settings at game level;

      - an explicit statement that GABS cannot infer whether existing values are common or
        profile-specific;

      - a skeleton for defining the requested profile without inventing its isolation
        values;

      - documentation anchor for launch profiles and the gabs-mcp skill name;
      - next actions: edit config → games_reload_config → games_show → retry games_start.

  - Do not add an automatic converter or rewrite the user’s current config. The two locally
    configured games remain separate because they represent different targets/launch modes;
    they can independently gain profiles later.

  ## Documentation and Installed Skill

  - Document profiles, named launch inputs, lifecycle status/stop/kill contracts, reload
    behavior, active-snapshot semantics, and the legacy manual-edit recipe using neutral
    game/container examples.

  - Update README.md, the configuration/integration/dynamic-tool guides, and example-
    config.json; run the existing public-surface genericity scan across all public docs and
    examples.

  - Update the repo-owned gabs-mcp skill concisely:
      - prefer named profiles over duplicate IDs when the target/launch mode is the same;
      - use named launch inputs only when the user explicitly requests the declared startup
        option;

      - never invent launch inputs or use them to recreate a control system that belongs in
        GABP tools;

      - follow the structured legacy conversion recipe when a requested profile is absent;
      - after config edits, call games_reload_config, verify its revision/result, then retry
        without restarting GABS or Codex;

      - stop/kill the active profile without guessing it.

  - Keep detailed schema examples in the configuration guide rather than bloating SKILL.md;
    ensure agents/openai.yaml still matches the skill metadata.

  - Add scripts/install-skills.sh plus make install-skills. The script validates the repo-
    owned skill, stages and atomically installs only skills/gabs-mcp into
    ${CODEX_HOME:-$HOME/.codex}/skills, preserves unrelated skills, and supports a check
    mode.

  - Run the install hook during local verification and compare the installed folder against
    the repository source. This closes the currently observed one-line drift between the two
    copies.

  ## Test and Acceptance Plan

  - Preserve all existing behavior tests for configs without profiles and confirm the
    current baseline remains green.

  - Add config validation tests for profile/default resolution, invalid names, reserved
    environment keys, lifecycle placeholders/commands, named-input types and constraints,
    unsupported launcher modes, and backward-compatible serialization.

  - Add pure resolver tests for argument ordering, environment precedence, profile hook
    inheritance, boolean/string/integer inputs, unknown profiles/inputs, and rejection of
    raw override-like fields.

  - Add MCP tests proving:
      - explicit and default profiles launch correctly;
      - omitted profile without a default is rejected with candidates;
      - duplicate profile starts do not create another process;
      - AI-facing metadata exposes declared names/constraints but not argv/env mappings or
        supplied values;

      - the legacy profile request returns the exact non-mutating manual conversion recipe
        and reload steps.

  - Add lifecycle tests using neutral helper processes/scripts for foreground and detached
    launches, status exit-code handling, timeouts, unknown state preservation, stop/kill
    priority, command failures, and absence of implicit shell interpretation.

  - Add runtime/session tests showing profile and lifecycle snapshots survive GABS restart/
    session takeover, config/profile edits, and removal/rename of an active game.

  - Add reload tests for automatic next-call reload, explicit forced reload, atomic file
    replacement, added/renamed profiles, invalid-file last-good behavior, blocked stale
    starts, active stop during invalid config, startup-only change reporting, and unchanged
    tools/list.

  - Add concurrent reload/call tests and run the relevant packages under the race detector.
  - Add CLI tests for --profile, repeated typed --input, missing/default profiles, status,
    stop, kill, and parity with MCP resolution.

  - Acceptance scenario: configure two profiles pointing at separate temporary data
    directories, launch each sequentially under one game ID, verify its arguments/
    environment and output stay inside the selected directory, verify the active profile in
    status, terminate it through the configured lifecycle hook, edit/rename a profile on
    disk, reload automatically, and launch the renamed profile without restarting GABS or
    the client.

  - Final verification: go test ./..., go test -race ./..., make build, public genericity
    scan, skill validation, skill install/check, and a clean working-tree review.

  ## Assumptions and Defaults

  - Only one profile may be active for a game ID. Concurrent instances continue to use
    separate game IDs.

  - Profiles are launch-context overlays, not embedded sub-games.
  - GABS selects and transports profile context; filesystem/container isolation remains the
    launcher/game integration’s responsibility.

  - Existing stopProcessName behavior remains a supported fallback.
  - Existing configs remain valid and are never rewritten automatically.
  - Profile-specific requests against legacy entries fail helpfully; ordinary legacy starts
    remain backward compatible and warning-free.

  - No GABP wire-version change is required. GABS_PROFILE is optional additional process
    metadata, while existing live bridge environment variables remain authoritative.
